# purpose-driven-book-study 详细用法

## 步骤 1：审读原书（Audit）

审读足够内容以判断：

- 作者意图与核心问题；
- 目标读者与先修知识；
- 全书论证/知识结构；
- 各章角色与依赖关系；
- 证据类型：实验、推导、案例、规范还是经验；
- 范围排除、平台假设、版本限制、翻译问题；
- 这本书能为用户的工作回答什么、不能回答什么。

长 PDF：先看元数据、目录、前言/引言、各章开头、章末小结、附录，再抽样代表性页面，然后才提路线。需要解析文件时用对应格式 skill（PDF → `mineru-pdf-parser` 或 `pdf`）。

## 步骤 2：全书定位图（Orientation Map）

细读前先呈现：

- 全书试图教会什么；
- 中心心智模型；
- 藏在章节结构背后的能力模块；
- 对当前工作主线的相关性与局限；
- 提议的问题驱动路线及顺序理由；
- 阶段边界与预期产出。

成为长期项目时，创建或更新 `00-学习路线与问题地图.md`（模板见 `references/document-templates.md`）。

## 步骤 3：问题驱动路线

每个模块填这张表：

| 字段 | 必填内容 |
|------|---------|
| 核心问题 | 学完后应能回答的问题 |
| 能力目标 | 应能解释/诊断/设计/验证什么 |
| 章节映射 | 对应章节/小节/页码，允许不连续 |
| 阅读深度 | 精读 / 支撑读 / 略读 / 暂缓 |
| 工作关联 | 对哪个任务、设计决策、故障模式、测试项有用 |
| 验证方式 | 习题、计算、代码、实验、画图或复述 |
| 阶段产出 | 要创建的总结文档或可复用产物 |

按概念依赖与工作价值排序。原书假设了用户缺失的知识、或做了平台特定断言时，允许针对性绕行到支撑资料。

## 步骤 4：教学单元（八步序列）

除非材料另有要求，按此顺序讲每个学习单元：

1. **提问**：我们要理解/决定什么？
2. **原书立场**：原书说了什么、在哪一页/节？
3. **机制**：在相关抽象层级上为什么是这样？（因果链优先于术语表）
4. **证据**：什么数据、推导、例子或规范支撑它？
5. **边界**：在什么架构、负载、版本、假设下成立？
6. **挑战**：什么反例、替代解释或权衡会改变结论？
7. **迁移**：怎么映射到用户当前的系统与工作主线？
8. **验证**：学习者可以怎么测试、测量或证伪这个结论？

先给心智模型，再深入机制与证据。前置概念按需补讲。图/表只在确实能澄清结构、时序、映射时使用。

## 步骤 5：来源纪律（四类标签）

全程显式区分：

- **原书观点**：原书明说或直接支撑的；
- **解读**：从原书推导出的综合或解释；
- **延伸**：应用到用户工作主线的部分；
- **验证**：来自规范、实验或当前权威资料的确认/反驳。

**不跨架构静默搬运结论**。例如：乱序服务器 CPU 的结论搬到顺序执行 MCU 时，必须显式说明什么变了；教科书解释性材料与厂商规范性文档冲突时，标明层级。对标准与参考手册，保留规范性语言、版本、寄存器条件、复位行为、实现定义边界——没有明确证据，不让二手资料覆盖一手规范。

## 步骤 6：阶段收尾

阶段以"能力建成"为结束标志，不以页码为标志。收尾动作：

1. 用因果链重建机制，而非复述章节；
2. 记录结论、证据、边界、未解决冲突、被纠正的旧认识；
3. 三层关联工作主线：现在直接可用的 / 可复用的工程方法 / 长期的架构与职业洞察；
4. 把洞察转成具体行动：测试、测量、代码检查、设计评审、后续问题；
5. 用模板创建 `阶段NN-主题总结.md`；
6. 路线有变就更新路线文档。

**不要每个小节都写浅总结**——只在有意义的概念里程碑、或用户明确要求 checkpoint 时落盘。

## 步骤 7：全书综合

学完全书或达成学习目标时产出：

- 按机制与工程问题组织的知识地图；
- 观点—证据—边界矩阵；
- 被本次学习改变的重要工作决策；
- 实验与未解决问题 backlog；
- 被有意暂缓的内容清单；
- "什么时候回来重读哪节"的索引。

## 互动风格

- 每次会话开场：说明当前阶段、核心问题、为什么现在学它。
- 邀请质疑与替代解释，不把书当天然正确。
- 显式纠正翻译、版本、平台错配。
- 用户插问：先完整回答，再把它接回路线。
- 用户的好例子、项目约束、已验证结论，吸收进下一阶段文档。
- 用户复述自己的理解求确认时（"对吧"）：严格验收——对的确认，偏的指出错在哪、为什么错，不附和。

## 本库内化细则

1. **落盘位置**：与用户确认专区（参考实现：`01_Hardware_硬件层/00_SoC_Design_Book_精读/`）。原始素材（PDF、MinerU 解析 full.md+images）入 `99_Attachments_附件`，消化产出入笔记层，引用方向单向：笔记 → 附件（CLAUDE.md §9.1 规则 12）。
2. **命名**：遵循 CLAUDE.md §3.2；读书专区可用系列前缀（如 `SoC_Book_Ch02_处理器子系统.md`）。落盘后 doc-review hook 自动校验，别绕过。
3. **笔记模板**：阶段总结用 `references/document-templates.md`，其中已并入 §9.2 要求的 关联笔记/标签/Agent 整理记录 三节。
4. **对话输出**：禁 LaTeX/Mermaid；公式纯文本、图用 ASCII（LRN-20260815-001）。
5. **方案确认**：路线制定/变更、专区创建、批量落盘前，先列方案等用户拍板（LRN-20260717-001）。
6. **疑点分级**：✅确定 / 🟡有出入 / ❓未验证，收尾输出时显式标注。
7. **学习点**：精读中犯错的、被纠正的、发现的好模式，实时记入 `.learnings/`（self-improving-agent）。

## 参考实现案例：SoC 设计基础教程精读（2026-08）

- 素材：`99_Attachments_附件/IC_Design_芯片设计/SoC设计基础教程_系统架构/full.md`（MinerU 解析 5133 行 + images）
- 路线：用户选定**按兴趣跳读**，首章 = 第 2 章 处理器子系统
- 沉淀：每章一篇笔记，专区集中存放
- 有效做法：一句话主线（锚到 `CPU 时间 = IC × CPI × Tclk`）→ 结构化要点 → 机制推导 → 工程连接（TC3xx/M7/R52）→ ✅🟡❓疑点 → 讨论点收尾；用户复述后严格验收（如"频率瓶颈是最慢一级而非最简单单元"的纠正）
- 移动端延伸：Kimi 项目指令与本 skill 同源（见 `references/kimi-code-instruction.md` 的简化变体）
