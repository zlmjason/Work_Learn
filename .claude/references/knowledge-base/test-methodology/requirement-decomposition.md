# 测试需求分解方法论

测试需求分解是芯片验证的起点。从系统需求到可执行的测试用例，需要经过系统化的分解过程。

## 分解流程

```
市场需求 (Market Requirements)
    ↓
系统需求 (System Requirements)
    ↓
芯片规格 (IC Specification) ← 你作为系统工程师的输出
    ↓
测试需求 (Test Requirements) ← 你作为验证工程师的输入
    ↓
测试方案 (Test Scheme)
    ↓
测试用例 (Test Cases)
```

## 分解方法

### 1. 功能分解

将芯片功能按层级分解：

```
MCU 功能
├── 核心功能
│   ├── Cortex-M7 运行
│   ├── NVIC 中断管理
│   ├── MPU 内存保护
│   └── Cache 管理
├── 通信外设
│   ├── CAN FD × 4
│   ├── LIN × 2
│   ├── Ethernet
│   ├── SPI × 3
│   └── I2C × 2
├── 模拟外设
│   ├── ADC × 2 (24 channels)
│   └── DAC × 2
├── 定时外设
│   ├── GPT × 8
│   ├── WDG × 2
│   └── RTC
└── 系统功能
    ├── 时钟/复位
    ├── 电源管理
    ├── DMA
    └── 调试
```

### 2. 测试类型分解

对每个功能模块，按测试类型分解：

| 测试类型 | 说明 | 示例 |
|---------|------|------|
| 功能测试 | 验证基本功能正确 | GPIO 输出高/低 |
| 边界测试 | 验证边界条件 | GPIO 最高翻转频率 |
| 错误测试 | 验证异常处理 | 向只读寄存器写入 |
| 性能测试 | 验证性能指标 | DMA 传输带宽 |
| 压力测试 | 验证极限条件 | 所有中断同时触发 |
| 兼容性测试 | 验证协议兼容 | CAN FD 与 CAN 2.0 混网 |
| 可靠性测试 | 验证长期稳定 | HTOL 1000 小时 |
| 安全测试 | 验证安全机制 | ECC 错误注入 |

### 3. 追溯矩阵

| 系统需求 ID | 描述 | 芯片规格 | 测试需求 ID | 测试方案 | 测试用例 |
|------------|------|---------|------------|---------|---------|
| SYS-001 | 支持 4 路 CAN FD | CAN 控制器 × 4 | TR-CAN-001 | CAN 功能验证 | TC_CAN_001 |
| SYS-002 | ASIL-D 安全等级 | Lockstep + ECC | TR-SAF-001 | 安全机制验证 | TC_SAF_001 |

## 分解原则

1. **完整性**：所有需求必须被覆盖（100% 需求覆盖率）
2. **独立性**：每个测试用例只验证一个功能点
3. **可重复**：测试用例必须可重复执行
4. **可判定**：测试结果必须明确（Pass/Fail）
5. **可追溯**：每个测试用例可以追溯到原始需求

## 工具

- Excel / Markdown：追溯矩阵
