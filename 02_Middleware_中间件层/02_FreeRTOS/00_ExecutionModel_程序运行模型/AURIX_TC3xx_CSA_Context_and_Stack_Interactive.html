0. 先建立一张不会混乱的总图

    Q -->|IRQ / Trap| I["Upper Context → CSA"]

最重要的第一句话是：

CSA 负责寄存器上下文；A10 指向的普通栈负责 C 语言栈数据。CSA 不是 USTACK，也不是 ISTACK。

如果只盯着 A10 指向的内存去回溯 TriCore 调用链，会漏掉 CSA 中的 Upper Context；如果只看 CSA，又会漏掉函数局部变量和栈溢出寄存器。

1. TriCore 有哪些程序员可见寄存器

TriCore TC1.6.2 有 32 个通用寄存器：

  • 16 个地址寄存器：A0～A15
  • 16 个数据寄存器：D0～D15

此外，还有决定控制流与上下文管理的关键状态寄存器：

  • PC：当前程序计数器
  • PSW：程序状态字
  • PCXI：Previous Context Information
  • FCX：Free CSA List Head Pointer
  • LCX：Free CSA List Limit Pointer
  • ISP：Interrupt Stack Pointer
  • ICR：Interrupt Control Register

1.1 地址寄存器与数据寄存器

地址寄存器主要用于：

  • 指针和地址计算
  • 栈访问
  • 基址寻址
  • 函数返回地址

数据寄存器主要用于：

  • 整数与位运算
  • 函数参数和返回值
  • 临时计算结果
  • Trap 的 TIN 信息

这里不要把“地址寄存器”理解为只能保存地址。架构和编译器主要按照上述用途使用它们，但本质上仍是 32-bit 寄存器。

1.2 几个有固定架构含义的寄存器

寄存器 架构角色 工程含义
A0 System Global Register 编译器通常用作短寻址全局/常量区基址
A1 System Global Register 编译器使用的全局数据基址之一
A8/A9 System Global Register 可保存系统级高频地址变量
A10 Stack Pointer，SP 当前真正参与普通栈访问的活动栈指针
A11 Return Address，RA CALL、IRQ、Trap 的返回控制流地址
A15 Implicit Address Register 一些短指令隐含使用的地址寄存器
D15 Implicit Data Register 一些短指令隐含使用；进入 Trap 时保存 TIN

1.3 为什么 A0、A1、A8、A9 特殊

这四个寄存器称为 System Global Registers：

A0、A1、A8、A9

它们不属于 Upper Context，也不属于 Lower Context，因此：

  • 普通 CALL/RET 不自动保存和恢复它们；
  • IRQ/Trap 入口与 RFE 不自动保存和恢复它们；
  • 不应被普通函数、ISR、Trap Handler 随意当作私有临时寄存器使用。

PSW.GW 控制当前执行流是否允许修改这四个全局地址寄存器：

PSW.GW 含义
0 禁止修改 A0/A1/A8/A9
1 允许修改 A0/A1/A8/A9

进入 IRQ 或 Trap 时，硬件把 PSW.GW 清零，避免异常处理程序无意破坏系统的全局基址约定。

2. 为什么上下文被分成 Upper 和 Lower

TriCore 不在每次调用或异常时无条件保存全部寄存器，而是把任务上下文拆成两组。

2.1 Upper Context

Upper Context 包含：

PCXI
PSW
A10～A15
D8～D15

一共 16 个 32-bit word，即 64 bytes。

它的核心特点是：

CALL、IRQ、Trap 会由硬件自动保存 Upper Context；RET/RFE 会由硬件自动恢复 Upper Context。

因此，可以把 Upper Context 理解为：

硬件自动为调用者或被中断者保护的寄存器状态。

但还要注意一个容易忽视的限制：在新的函数、ISR 或 Trap Handler 中，除了架构明确定义的寄存器外，不应假定其他 Upper 寄存器继承了进入前的值。

架构明确定义的入口值主要包括：

  • A10：当前栈指针
  • A11：当前返回地址
  • PSW/PCXI：新的控制与上下文链状态
  • Trap 入口时的 D15 = TIN

2.2 Lower Context

Lower Context 包含：

PCXI
A11
A2～A7
D0～D7

同样是 16 个 32-bit word，即 64 bytes。

它的核心特点是：

CALL、IRQ、Trap 不自动保存 Lower Context；需要软件通过 BISR 或 SVLCX 显式保存，并用 RSLCX 恢复。

Lower Context 适合承担：

  • 函数参数传递
  • 函数返回值传递
  • 调用者与被调用者约定保存的寄存器
  • ISR 需要时才付出保存成本的寄存器集合

2.3 为什么不在异常入口一次性保存全部寄存器

设计目标是降低确定性响应延迟。

如果每个 IRQ 都先保存全部 GPR：

  • 极短 ISR 也要承担完整现场保存开销；
  • 总线和本地 RAM 产生更多访问；
  • 高优先级控制中断的第一条有效业务指令更晚执行。

TriCore 的做法是：

  1. 硬件固定保存 Upper Context；
  2. ISR 可以先使用已被保护的 Upper 寄存器做最紧急的动作；
  3. 如果后续需要 Lower 寄存器或需要调用函数，再执行 BISR/SVLCX；
  4. 返回前用 RSLCX 恢复 Lower Context。

这是一种“固定低延迟入口 + 按需扩展现场”的设计。

2.4 总分类表

寄存器/状态 分类 CALL 自动保存 IRQ/Trap 自动保存

A2～A7 Lower 否 否

2.5 为什么 A11 和 PCXI 同时出现在两种 Context 中

这不是重复设计，而是在两个不同时间点保存两条不同的返回链。

以 ISR 为例：

  1. IRQ 入口先把被中断任务的 Upper Context 保存到 CSA_U；
  2. 硬件为 ISR 设置新的 A11 和新的 PCXI；
  3. ISR 如果执行 BISR，会把 ISR 当前的 A11/PCXI 保存到 CSA_L；
  4. ISR 内即使又发生 CALL，返回前也能用 RSLCX 恢复异常返回链；
  5. 最后 RFE 根据恢复后的 A11/PCXI 返回原任务。
flowchart TD
    T["任务状态"] --> U["IRQ：Upper CSA 保存任务 A11/PCXI"]
    U --> H["ISR 获得新的 A11/PCXI"]
    H --> L["BISR：Lower CSA 保存 ISR 的 A11/PCXI"]
    L --> R1["RSLCX：恢复 ISR 异常返回链"]
    R1 --> R2["RFE：恢复任务 Upper Context"]

一句话区分：

Upper CSA 里的 A11/PCXI 属于被打断或发起调用的一方；Lower CSA 里的 A11/PCXI 属于显式保存 Lower Context 时的当前执行流。

3. CSA 到底是什么

CSA 全称 Context Save Area。

它不是 CPU 内部隐藏寄存器，而是软件预先在可用 RAM 中划出并初始化的一组固定大小内存块。

每个 CSA：

16 words × 4 bytes = 64 bytes

并且必须按 64 bytes 对齐。

一个 CSA 一次只能保存：

  • 一个 Upper Context，或
  • 一个 Lower Context。

不能在同一个 CSA 中同时放置完整 Upper 和 Lower Context。

相同的 64-byte 尺寸带来两个工程优势：

  • 上下文分配和回收使用同一套链表机制；
  • 地址计算和上下文搬运可以采用固定序列，硬件时序更可预测。

3.3 CSA 指针不是普通 32-bit 地址

FCX、LCX 和 PCXI.PCX 里的 CSA 指针使用压缩格式：

pointer[19:16] = Segment
pointer[15:0]  = Offset

有效地址构造为：

EA[31:28] = Segment
EA[27:22] = 0
EA[21:6]  = Offset
EA[5:0]   = 0

对应 C 语言公式：

uint32_t csa_ptr_to_addr(uint32_t csa_ptr)
{
    return ((csa_ptr & 0x000F0000u) << 12) |
           ((csa_ptr & 0x0000FFFFu) << 6);
}

反向转换：

uint32_t addr_to_csa_ptr(uint32_t addr)
{
    return ((addr >> 12) & 0x000F0000u) |
           ((addr >> 6)  & 0x0000FFFFu);
}

示例：

CSA 实际地址 = 0x7001_0000
Segment       = 0x7
Offset        = 0x0400
CSA pointer   = 0x0007_0400

因此调试器里看到：

PCXI.PCX = 0x00070400

不能直接把它当成 0x00070400 的 RAM 地址；解码后才是 0x70010000。

最低 6 bit 不参与存储，天然保证 64-byte 对齐。每个 256 MB segment 中，CSA 指针可覆盖其中固定的 4 MB CSA 地址范围，对应最多 2^16 个 CSA。

3.4 CSA 不能随便放在哪里

架构层面的基本限制包括：

  • 不能放在带 peripheral-space 属性的内存段；
  • 不能放在启用 MMU 后需要地址转换的内存区域；
  • 还要满足具体 TC3xx 产品对可用 RAM、可访问路径和局部存储的额外约束。

3.5 软件直接读取活动 CSA 前为什么要 DSYNC

实现可能在 CPU 内部暂存活动 CSA 的寄存器状态，以提高上下文保存性能。因此内存中的 CSA 镜像可能尚未反映最新内部状态。

软件或调试辅助代码如果要直接访问活动 CSA，应先执行：

dsync

DSYNC 会确保内部缓冲的 CSA 状态已经提交到内存。它并不等于无效化 D-Cache，二者不能混为一谈。

4. 三个关键指针：FCX、PCXI.PCX、LCX

4.1 FCX：空闲 CSA 链表头

FCX → 第一个空闲 CSA

空闲 CSA 的第一个 word 是 Link Word，指向下一个空闲 CSA。

FCX → CSA3 → CSA4 → CSA5 → NULL

每次发生 Upper 或 Lower Context Save，CPU 都从 FCX 指向的链头取走一个 CSA。

4.2 PCXI.PCX：当前使用中的上下文链表头

PCXI.PCX 指向最近保存的上下文：

PCXI.PCX → 最新 CSA → 上一个 CSA → 更早的 CSA

这条链可以包含交错的 Upper CSA 与 Lower CSA；PCXI.UL 用于说明当前链头是哪一种上下文。

4.3 LCX：接近耗尽的警戒点

LCX 不是空闲链表尾指针，也不是“最多允许使用到这里”的硬限制。它是一个预警位置。

当一次 Context Save 使用的 CSA 满足：

旧 FCX == LCX

则：

  1. 本次保存操作完成；
  2. FCX 已经推进到下一个 CSA；
  3. 随后触发 Class 3 / TIN 1 的 FCD Trap。

因此 FCD 表示“即将耗尽”，不是“本次保存失败”。

架构手册还要求考虑安全余量：

  • FCD Trap 自身还需要一个 CSA；
  • FCD Handler 期间可能再来一个异步 Trap，又需要一个 CSA；
  • 如果 FCD Handler 自己执行 CALL，还要继续增加余量。

所以 LCX 不能指向真正的最后一个空闲 CSA。至少要在 LCX 之后保留两个 CSA；实际安全软件通常根据可嵌套 Trap 和 Handler 调用深度预留更多。

5. CSA 保存与恢复的链表本质

5.1 保存前

Free List:
FCX → CSA3 → CSA4 → CSA5

Previous Context List:
PCXI.PCX → CSA2 → CSA1

5.2 保存操作

可抽象为：

used_csa = FCX;
new_fcx  = used_csa->link_word;

/* 第一个 word 改为旧 PCXI，接到使用链上 */
used_csa->link_word = old_PCXI;

/* 其余 15 words 写入 Upper 或 Lower Context */
save_selected_context(used_csa);

/* 当前 CSA 成为新链头 */
PCXI.PCX = used_csa;
PCXI.UL  = context_type;

/* 空闲链表向后推进 */
FCX = new_fcx;

保存后：

Free List:
FCX → CSA4 → CSA5

Previous Context List:
PCXI.PCX → CSA3 → CSA2 → CSA1

5.3 恢复操作

恢复前：

PCXI.PCX → CSA3 → CSA2 → CSA1
FCX      → CSA4 → CSA5

可抽象为：

used_csa = PCXI.PCX;
old_pcxi = used_csa->link_word;

restore_selected_context(used_csa);

/* 释放的 CSA 插回 Free List 头部 */
used_csa->link_word = FCX;
FCX = used_csa;

/* Previous Context List 回退一层 */
PCXI = old_pcxi;

恢复后：

PCXI.PCX → CSA2 → CSA1
FCX      → CSA3 → CSA4 → CSA5

5.4 一句话记忆

保存：Free List 出栈，Previous List 入栈
恢复：Previous List 出栈，Free List 入栈

这里的“栈”是链表操作意义上的 LIFO，不是 A10 指向的普通内存栈。

6. PCXI 为什么不只是一个地址指针

PCXI 的关键字段包括：

字段 含义
PCPN Previous CPU Priority Number
PIE Previous Interrupt Enable
UL 当前 PCX 指向 Upper 还是 Lower CSA
PCXS CSA Segment
PCXO CSA Offset

其中：

UL = 1：链头为 Upper Context
UL = 0：链头为 Lower Context

恢复指令会检查类型：

  • RET/RFE 要恢复 Upper；如果 UL=0，触发 CTYP Trap；
  • RSLCX 要恢复 Lower；如果 UL=1，触发 CTYP Trap。

因此 PCXI 同时承担：

  1. Previous Context List 的链头；
  2. 当前链头的上下文类型；
  3. 异常前的中断使能和 CPU 优先级信息。

7. 普通 CALL/RET 到底发生了什么

7.1 CALL 的硬件动作

以普通 CALL 为主线，可按下面顺序理解：

  1. 检查 FCX 是否为空；为空则触发 FCU；
  2. 根据 PSW.CDE/CDC 做调用深度检查；
  3. 记住返回地址，即 CALL 后的下一条指令地址；
  4. 从 FCX 取出一个空闲 CSA；
  5. 保存调用者的 Upper Context；
  6. 把新 CSA 挂到 PCXI.PCX 链头，并令 PCXI.UL=1；
  7. FCX 指向下一个空闲 CSA；
  8. PC 跳到被调用函数；
  9. A11 更新为返回地址；
  10. 如果本次使用的旧 FCX == LCX，触发 FCD。
sequenceDiagram
    participant Caller as 调用者
    participant CPU as TriCore
    participant CSA as CSA 链表
    participant Callee as 被调用函数
    Caller->>CPU: CALL target
    CPU->>CSA: 从 FCX 取 CSA
    CPU->>CSA: 保存调用者 Upper Context
    CPU->>CPU: PCXI.PCX 指向新 CSA
    CPU->>CPU: A11 = 返回地址
    CPU->>Callee: PC = target

7.2 CALL 与 A10 普通栈的关系

普通 CALL 不切换到 ISTACK，也不会自动为局部变量分配普通栈空间。

调用前后：

  • A10 仍指向当前任务的同一条普通栈；
  • 编译器生成的函数序言可能调整 A10，为局部变量和 spill 分配空间；
  • 调用者 Upper Context 在 CSA 中；
  • 栈局部数据在 A10 指向的 RAM 中。

所以一个函数调用可能同时产生两类存储开销：

固定上下文开销：1 个 Upper CSA = 64 bytes
普通栈开销：由函数局部变量、ABI、优化等级和寄存器分配决定

7.3 RET 的硬件动作

RET 执行时：

  1. 检查调用深度是否下溢；
  2. 检查 PCXI.PCX != 0，否则 CSU；
  3. 检查 PCXI.UL == 1，否则 CTYP；
  4. 先以当前 A11 形成返回目标 PC；
  5. 从 PCXI.PCX 指向的 CSA 恢复调用者 Upper Context；
  6. 把这个 CSA 插回 Free List 头部；
  7. 恢复旧 PCXI 和 PSW；
  8. 跳回调用者。

一个关键细节是：

返回目标来自执行 RET 前当前上下文的 A11；而 CSA 中保存的旧 A11 会作为调用者自己的 RA 被恢复，用于更外层返回。

这就是多层调用可以连续展开的原因。

7.4 Lower Context 为什么不随 CALL 自动保存

被调用函数会直接看到调用者留下的 Lower 寄存器值，因此它们适合用于参数和返回值。

这要求编译器与 ABI 明确约定：

  • 哪些 Lower 寄存器可由被调用者改写；
  • 哪些需要由调用者提前保护；
  • 哪些用于参数和返回值。

Lower Context 的行为更接近传统 ABI 中的 caller-saved/callee-saved 协作，而 Upper Context 是 TriCore 用 CSA 实现的硬件私有调用上下文。

7.5 FCALL/FRET 与普通 CALL/RET 的区别

FCALL 用于不需要完整 Upper Context 切换的快速调用：

  • 不分配 CSA；
  • 只把旧 A11 保存到 A10 指向的普通栈；
  • 被调用函数与调用者共享其他寄存器上下文；
  • FRET 从普通栈恢复旧 A11。

它降低 CSA 开销，但把更多寄存器协作责任交给编译器和程序员，不能把它当作普通 CALL 的无条件替代品。

8. IRQ 入口：Upper CSA、A11、ISP 和 PSW.IS 如何配合

8.1 中断被接受的基本条件

普通可屏蔽中断进入前，CPU 至少要满足：

ICR.IE == 1
ICR.PIPN > ICR.CCPN

并且 CPU 当前没有处于禁止立即响应中断的架构阶段，例如正在执行不可中断的入口序列或某些多周期操作。

8.2 进入 ISR 的主要动作

CPU 接受中断后，主要完成：

  1. 保存当前任务的 Upper Context 到 CSA；
  2. 设置 A11 为被中断程序的恢复地址；
  3. 如果旧 PSW.IS=0，执行 A10 ← ISP；
  4. 设置 PSW.IS=1；
  5. 设置 Supervisor 权限与保护寄存器组等异常入口状态；
  6. 清零并重新配置当前 Call Depth 状态；
  7. 清零 PSW.GW，禁止修改全局地址寄存器；
  8. 把旧 ICR.IE/CCPN 保存到新 PCXI.PIE/PCPN；
  9. ICR.IE=0，并把当前中断优先级装入 ICR.CCPN；
  10. 从中断向量表取得 ISR 入口。
flowchart TD
    A["接受 IRQ"] --> B["Upper Context → CSA"]
    B --> C["A11 ← 恢复地址"]
    C --> D{"旧 PSW.IS = 0？"}
    D -->|是| E["A10 ← ISP"]
    D -->|否| F["A10 保持当前值"]
    E --> G["PSW.IS ← 1；IE ← 0"]
    F --> G
    G --> H["取中断向量，执行 ISR"]

8.3 为什么必须先保存 A10，再把 A10 改成 ISP

A10 本身属于 Upper Context。

如果 CPU 先执行：

A10 = ISP

再保存 Upper Context，那么原任务的栈指针就丢失了。

正确因果链是：

先把旧 A10、旧 PSW.IS 保存到 Upper CSA
→ 再根据旧 PSW.IS 决定是否加载 ISP
→ RFE 时从 Upper CSA 恢复原 A10 和 PSW.IS

8.4 为什么 ISR 刚进入时中断是关闭的

ISR 入口时 ICR.IE=0，让 Handler 有机会完成不可被打断的最小序言，例如：

  • 保存 Lower Context；
  • 调整当前优先级；
  • 处理必须原子完成的设备状态；
  • 建立软件要求的异常框架。

之后可以选择：

  • ENABLE：只重新开启中断；
  • BISR #priority：保存 Lower Context、设置 CCPN 并重新开启中断；
  • 保持关闭，执行不可嵌套 ISR。

9. BISR、SVLCX、RSLCX：什么时候需要 Lower Context

9.1 三条指令的区别

指令 CSA 动作 额外中断动作 典型用途
SVLCX 保存 Lower Context，UL=0 不改变 IE/CCPN 只需要显式保护 Lower Context
BISR #n 保存 Lower Context，UL=0 ICR.CCPN=n，ICR.IE=1 标准 ISR 序言/允许嵌套
RSLCX 恢复 Lower Context并回收 CSA 无 在 RFE 前恢复 Lower Context

9.2 极小 ISR 可以不保存 Lower Context

如果 ISR：

  • 完全使用已经自动保护的 Upper 寄存器；
  • 不调用会破坏 Lower 寄存器的函数；
  • 不需要开放中断嵌套；

则可以直接完成工作后执行 RFE，不必额外消耗一个 Lower CSA。

概念流程：

IRQ
→ 自动保存 Upper
→ 用 Upper 寄存器完成极短处理
→ RFE

9.3 典型 C ISR 为什么通常需要保存 Lower Context

C 编译器生成的代码可能使用参数寄存器、临时寄存器，或者调用其他 C 函数，这些操作可能改写 Lower Context。

因此典型流程是：

IRQ 自动保存 Upper
→ BISR 保存 Lower，并按设计重新开中断
→ 执行 C ISR / 调用函数
→ RSLCX 恢复 Lower
→ RFE 恢复 Upper 并返回
sequenceDiagram
    participant Task as 被中断任务
    participant HW as 硬件入口
    participant ISR as ISR
    participant CSA as CSA 链
    Task->>HW: IRQ accepted
    HW->>CSA: 保存 Task Upper
    HW->>ISR: 进入 ISR，IE=0
    ISR->>CSA: BISR 保存 Lower
    ISR->>ISR: IE=1，执行业务/允许嵌套
    ISR->>CSA: RSLCX 恢复 Lower
    ISR->>HW: RFE
    HW->>CSA: 恢复 Task Upper
    HW->>Task: 返回原控制流

9.4 为什么 BISR 不一定是 ISR 第一条指令

如果响应时间极敏感，ISR 可以先只用 Upper 寄存器完成最紧急操作，例如：

  • 读取并锁存一个会快速变化的状态；
  • 清除必须尽快响应的硬件握手；
  • 记录时间戳；

随后再执行 BISR，进入可以使用 Lower 寄存器和允许更高优先级嵌套的阶段。

但边界非常严格：

在 BISR/SVLCX 之前，不能先改写随后想要保存的 Lower 寄存器，否则保存下来的已经不是被中断任务的原值。

10. Trap 与 IRQ 的相同点和不同点

10.1 相同点

正常 Trap 入口同样会：

  • 自动保存 Upper Context；
  • 更新 A11；
  • 如果旧 PSW.IS=0，把 ISP 装入 A10；
  • 设置 PSW.IS=1；
  • 进入 Supervisor mode；
  • 清零 PSW.GW；
  • 关闭普通中断；
  • 通过 RFE 恢复原执行流。

10.2 Trap 特有信息

Trap 入口会设置：

D15 = TIN

Handler 由 Trap Class 和 TIN 共同判断具体原因。

10.3 A11 中的返回地址因 Trap 类型不同

事件 新 A11 的语义
普通 CALL CALL 后的下一条指令
IRQ 被中断后下一条应执行的指令
异步 Trap 下一条应执行的指令
SYSCALL SYSCALL 后的下一条指令
一般同步 Trap 触发 Trap 的指令地址

同步 Trap 返回到故障指令，意味着 Handler 必须修复原因、调整状态或选择其他恢复策略；否则 RFE 后可能再次触发同一 Trap。

10.4 FCU 是特殊的不可恢复情况

如果 FCX=0 时仍试图保存上下文，会触发 FCU。由于 Upper Context 无法完成保存，部分原架构状态已经丢失。

因此：

FCU 通常被视为不可恢复系统错误，Handler 的最终动作应进入受控复位或其他安全状态，而不是尝试正常 RFE。

11. PSW.IS、A10、ISP、USTACK、ISTACK 的准确关系

这是最容易与 Cortex-M7 混淆的部分。

11.1 AURIX 真正参与栈寻址的只有 A10

A10 = 当前活动 Stack Pointer

无论普通任务还是 ISR，编译器生成的普通栈访问最终都使用 A10。

所谓 USTACK 和 ISTACK，本质上是链接脚本或 RTOS 在 RAM 中规划的不同区域，而不是两套会自动同时递增/递减的活动硬件 SP。

11.2 ISP 是“首次异常切栈时的装载源”

每个 TriCore CPU 核有自己的 CPUx_ISP。启动软件通常把它初始化为本核 ISTACK 的栈顶。

CPU0_ISP = CPU0_ISTACK_TOP
CPU1_ISP = CPU1_ISTACK_TOP
...

进入第一层异常时，如果旧 PSW.IS=0：

A10 = ISP

ISR 后续的压栈、局部变量分配只改变 A10，不会让 ISP 跟随变化。

因此 ISP 更准确的理解是：

从用户栈首次进入异常栈时，提供给 A10 的入口值。

11.3 PSW.IS 是什么，不是什么

PSW.IS 架构含义
0 当前执行流被视为使用 User Stack
1 当前执行流被视为使用 Shared Global/Interrupt Stack

PSW.IS 用于异常入口的栈切换判断，但它不是：

  • 另一个栈指针；
  • 内存地址范围比较器；
  • 栈访问权限保护；
  • 自动跟踪 A10 实际落在哪段 RAM 的硬件状态机。

单独把 PSW.IS 写成 1，并不会立即执行 A10=ISP。只有 IRQ/Trap 入口序列会根据进入前的 PSW.IS 判断是否装载 ISP。

11.4 USTACK/ISTACK 与 IS 状态必须保持一致

如果软件错误造成：

A10 指向 USTACK
PSW.IS = 1

下一次异常会认为当前已经在 ISTACK，不再加载 ISP，导致 Handler 继续使用 USTACK。

反过来：

A10 指向 ISTACK
PSW.IS = 0

下一次异常会重新执行 A10=ISP，可能覆盖当前异常栈中仍然有效的数据。

因此，PSW.IS 是软件必须维护正确的架构状态，而不是保护机制。

11.5 “Shared Global Stack”共享到什么范围

这里的共享通常表示：

  • 同一个 CPU 核上的 IRQ 和 Trap 共享该核 ISTACK；
  • 同核嵌套异常在同一 ISTACK 上继续向下使用；
  • 并不表示 TC3xx 所有 CPU 核共用同一个物理中断栈。

工程上通常为每个核独立配置：

CPU0 USTACK / CPU0 ISTACK / CPU0 ISP
CPU1 USTACK / CPU1 ISTACK / CPU1 ISP
...

12. 第一层中断与嵌套中断的完整例子

12.1 初始任务状态

假设：

A10    = 0x7001_FF00   // Task USTACK 当前 SP
PSW.IS = 0
ISP    = 0x7003_FF00   // CPU0 ISTACK 栈顶

12.2 第一层 IRQ 进入

Upper CSA1 保存：

CSA1.A10    = 0x7001_FF00
CSA1.PSW.IS = 0

随后硬件设置：

A10    = 0x7003_FF00
PSW.IS = 1

第一层 ISR 执行一段代码后，假设普通栈变成：

A10 = 0x7003_FE80

12.3 第二层更高优先级 IRQ 进入

此时旧 PSW.IS=1，所以硬件不会重新把 ISP 装入 A10。

Upper CSA2 保存：

CSA2.A10    = 0x7003_FE80
CSA2.PSW.IS = 1

第二层 ISR 从当前 ISTACK 位置继续向下使用，例如：

A10 = 0x7003_FE00

12.4 第二层 RFE

恢复 CSA2：

A10    = 0x7003_FE80
PSW.IS = 1

返回第一层 ISR 的中断栈现场。

12.5 第一层 RFE

恢复 CSA1：

A10    = 0x7001_FF00
PSW.IS = 0

返回原任务及其 USTACK。

sequenceDiagram
    participant T as Task / USTACK
    participant U1 as Upper CSA1
    participant I1 as IRQ1 / ISTACK
    participant U2 as Upper CSA2
    participant I2 as IRQ2 / ISTACK
    T->>U1: 保存 A10=Task_SP, IS=0
    U1->>I1: A10=ISP, IS=1
    I1->>U2: 保存 A10=IRQ1_SP, IS=1
    U2->>I2: 保留当前 A10
    I2->>U2: RFE 恢复 IRQ1_SP
    U2->>I1: 继续 IRQ1
    I1->>U1: RFE 恢复 Task_SP
    U1->>T: 继续任务

最关键的设计理由是：

嵌套 IRQ 不能每次都把 A10 重装为 ISTACK_TOP，否则内层 ISR 会覆盖外层 ISR 已经使用的栈空间。

13. ISR 内再调用函数时，CSA 链如何增长

假设任务被 IRQ 打断，ISR 执行 BISR 后又调用函数 foo()：

步骤 1：IRQ 入口
  分配 Upper CSA_U0，保存任务 Upper

步骤 2：BISR
  分配 Lower CSA_L0，保存任务/异常入口可见的 Lower

步骤 3：ISR CALL foo
  分配 Upper CSA_U1，保存 ISR 调用者 Upper

步骤 4：foo RET
  恢复并释放 CSA_U1

步骤 5：ISR RSLCX
  恢复并释放 CSA_L0

步骤 6：ISR RFE
  恢复并释放 CSA_U0

链头类型变化：

IRQ 后：          PCXI → U0，UL=1
BISR 后：         PCXI → L0 → U0，UL=0
CALL foo 后：     PCXI → U1 → L0 → U0，UL=1
foo RET 后：      PCXI → L0 → U0，UL=0
RSLCX 后：        PCXI → U0，UL=1
RFE 后：          回到 IRQ 发生前的 PCXI

这也解释了为什么顺序必须匹配：

CALL       ↔ RET
BISR/SVLCX ↔ RSLCX
IRQ/Trap   ↔ RFE

如果跳过 RSLCX 直接 RFE，此时 PCXI.UL=0，而 RFE 要求 Upper Context，于是触发 CTYP。

14. AURIX 与 Cortex-M7 栈/异常模型对比

14.1 Cortex-M7 确实有两个独立 SP

Cortex-M7 有：

MSP：Main Stack Pointer
PSP：Process Stack Pointer

两者是同时存在、各自保持数值的硬件寄存器。

Cortex-M7 执行状态 活动 SP
Thread mode，CONTROL.SPSEL=0 MSP
Thread mode，CONTROL.SPSEL=1 PSP
Handler mode MSP

RTOS 中常见配置是：

任务 Thread mode → PSP
异常 Handler mode → MSP

任务被异常打断后，PSP 仍作为独立寄存器存在；Handler 改用 MSP，不需要先把 PSP 保存到某个 CSA 才能记住任务栈指针。

14.2 M7 异常硬件栈帧压在哪里

异常入口时，Cortex-M7 会把基本栈帧压入异常发生前所使用的栈：

R0, R1, R2, R3, R12, LR, PC, xPSR

典型 RTOS 场景：

异常前：Thread 使用 PSP
→ 基本硬件栈帧压入 PSP 指向的任务栈
→ 进入 Handler mode
→ Handler 使用 MSP

如果异常发生在 Handler mode，则原本就在使用 MSP，嵌套异常的硬件栈帧继续压入 MSP。

若启用 FPU，还要考虑扩展栈帧和 Lazy Stacking；这不改变 MSP/PSP 是两个独立 SP 的基本事实。

14.3 AURIX 异常现场放在哪里

AURIX 的基本模型是：

Upper 寄存器现场        → Upper CSA
需要时的 Lower 现场     → Lower CSA
ISR/Trap 的 C 栈数据     → A10 指向的 ISTACK
被中断任务的普通栈数据   → 原 USTACK，保持不动

第一层异常入口时，任务原 A10 不是保存在一个独立 USP 中，而是保存在 Upper CSA 中。

14.4 核心差异表

对比项 Cortex-M7 AURIX TC3xx / TriCore
硬件活动 SP MSP 与 PSP 两个独立 SP 一个活动 A10/SP
任务栈 常用 PSP A10 指向 USTACK，PSW.IS=0
异常栈 Handler 固定使用 MSP A10 指向 ISTACK，PSW.IS=1
异常栈入口值 MSP 本身持续变化 ISP 仅在首次切栈时装入 A10
Thread 栈选择 CONTROL.SPSEL 无 MSP/PSP 式运行时二选一
异常硬件现场 基本帧压入异常前活动栈 Upper Context 保存到 CSA
未自动保存寄存器 如 R4～R11 由软件处理 Lower Context 按需 BISR/SVLCX
异常返回标识 LR 中的 EXC_RETURN A11 + PCXI + CSA
嵌套异常栈 Handler 一直使用 MSP IS=1，保留当前 A10 继续用 ISTACK
普通函数调用 BL 写 LR；编译器按需用栈保存 普通 CALL 自动分配 Upper CSA
调用链回溯 SP/LR/调试展开信息 A10 普通栈 + A11 + CSA 链 + 调试信息

14.5 两种架构最容易发生的错误类比

错误类比：

AURIX ISP == Cortex-M MSP
AURIX USTACK == Cortex-M PSP

更准确的说法是：

Cortex-M：MSP/PSP 是两个持续存在、独立变化的 SP。

AURIX：A10 是唯一当前活动 SP；
       ISP 是首次异常切入 ISTACK 时提供给 A10 的值；
       任务旧 A10 依靠 Upper CSA 保存。

15. 上下文管理相关 Trap

Class 3 是 Context Management Trap。

TIN 名称 触发条件 工程含义
1 FCD Context Save 使用了 LCX 指向的 CSA 接近耗尽；本次保存已完成
2 CDO CALL 时 Call Depth Counter 溢出 可能递归失控或深度预算不足
3 CDU RET 时 Call Depth Counter 下溢 返回层次或软件深度管理异常
4 FCU FCX=0 仍尝试保存，或 Context 操作失败 状态丢失，通常不可恢复
5 CSU 恢复时 PCXI.PCX=0 上下文链下溢/任务初始化错误
6 CTYP 恢复指令与 PCXI.UL 类型不匹配 RET/RFE/RSLCX 配对或链表错误
7 NEST Call Depth 非零时执行 RFE ISR/Trap 内仍有未退出的普通 CALL

15.1 FCD 与 FCU 的本质差异

FCD：还能完成本次保存，是“预警”
FCU：无法完成本次保存，是“状态已经丢失”

测试和安全反应中不能把二者用同一恢复策略处理。

15.2 NEST 为什么能发现错误返回路径

正常 ISR 内的函数调用必须先逐层 RET，让 Call Depth 回到异常入口层，再执行 RFE。

如果在被调用函数内部直接跳到 RFE：

  • 当前还有普通 CALL 产生的 Upper CSA 留在链上；
  • RFE 会绕过正确的 RET；
  • Call Depth 非零触发 NEST，阻止链表被错误展开。

只看 A10 或只看 PCXI 都不够。

16.2 断点位置

建议依次在以下位置停住：

  1. 普通函数 CALL 前；
  2. 被调用函数第一条指令；
  3. RET 前；
  4. IRQ 触发前的任务代码；
  5. 中断向量第一条指令；
  6. BISR 后；
  7. RSLCX 前后；
  8. RFE 前后；
  9. 嵌套 IRQ 的第二层入口。

16.3 每个断点要记录什么

时点 重点记录
CALL 前 A10/A11/PCXI/FCX
CALL 后 新 A11、PCXI.UL=1、FCX 是否前移
IRQ 第一条 A10 是否等于 ISP、PSW.IS、PCXI.PIE/PCPN
BISR 后 PCXI.UL=0、FCX 再前移、ICR.IE 是否开启
嵌套 IRQ 第一条 A10 是否保留外层 ISR 当前值，而不是回到 ISP

16.4 解码 PCXI 指向的 CSA

#define CSA_PTR_MASK   (0x000FFFFFu)
#define CSA_UL_MASK    (1u << 20)

static uint32_t csa_effective_address(uint32_t pcxi_or_fcx)
{
    uint32_t p = pcxi_or_fcx & CSA_PTR_MASK;
    return ((p & 0x000F0000u) << 12) |
           ((p & 0x0000FFFFu) << 6);
}

访问活动 CSA 前，在目标代码允许的情况下先执行 DSYNC。调试器是否会自动处理内部缓冲依赖具体探针和调试实现，不能一概假定。

16.5 调用栈为什么不能只扫描 A10

TriCore 的函数返回关系分散在：

  • 当前 PC；
  • 当前 A11；
  • PCXI 指向的 CSA 链；
  • A10 指向的普通内存栈；
  • 编译器生成的 DWARF/unwind 信息；
  • FCALL 放到普通栈里的旧 A11。

因此，调试器要正确显示完整 Call Stack，必须理解 TriCore ABI 和 CSA 链，而不能使用简单的传统 SP 扫描算法。

17. 建议做的系统验证用例

用例 1：单层 CALL/RET 的 CSA 守恒

目的：验证普通调用对 FCX/PCXI 的影响。

步骤：

  1. 记录 CALL 前 FCX、PCXI、A11；
  2. 单步执行 CALL；
  3. 验证 FCX 指向下一个空闲 CSA；
  4. 验证 PCXI.PCX 指向刚使用的 CSA、UL=1；
  5. 检查 Upper CSA 内容；
  6. 执行 RET；
  7. 验证原 CSA 回到 Free List 头部。

期望：一次 CALL 消耗一个 Upper CSA，一次 RET 完整归还。

用例 2：IRQ 从 USTACK 切换到 ISTACK

目的：验证 PSW.IS=0 的首次异常切栈。

前置状态：

A10 指向任务 USTACK
PSW.IS = 0
ISP 指向独立 ISTACK

期望：

  • Upper CSA 中保存旧 A10 与旧 IS=0；
  • ISR 第一条指令处 A10=ISP；
  • PSW.IS=1；
  • RFE 后恢复原 A10 和 IS=0。

用例 3：嵌套 IRQ 不重复加载 ISP

目的：验证第二层中断继续使用当前 ISTACK。

步骤：

  1. 外层 ISR 通过局部变量让 A10 离开 ISTACK_TOP；
  2. 开启更高优先级中断；
  3. 触发内层 IRQ；
  4. 在内层第一条指令记录 A10。

期望：内层入口 A10 等于外层被打断时的 A10，而不是等于 ISP。

用例 4：BISR/RSLCX 配对

目的：验证 Lower CSA 的分配与回收。

期望：

  • IRQ 后 UL=1；
  • BISR 后 UL=0，并额外消耗一个 CSA；
  • RSLCX 后链头恢复为 Upper、Lower CSA 被回收；
  • RFE 正常返回。

用例 5：故意跳过 RSLCX

目的：验证 CTYP Trap。

步骤：BISR 后直接执行 RFE。

期望：因为 PCXI.UL=0 而触发 Class 3 / TIN 6 CTYP。

该用例属于故障注入，应在隔离测试环境中执行，并确保 Trap Table、ISTACK 和复位恢复路径已正确配置。

用例 6：FCD 预警

目的：验证 LCX 是预警点而不是最后一个 CSA。

步骤：在受控环境中缩短 Free List，并令一次 Context Save 使用 LCX 指向的 CSA。

期望：

  • 本次 Context Save 已完成；
  • 随后进入 FCD Handler；
  • Handler 仍有安全保留 CSA 可用。

用例 7：PSW.IS 与 A10 故意不一致

目的：证明 PSW.IS 不做地址范围检查。

该测试风险较高，只建议在仿真、验证平台或有完整恢复机制的测试镜像中进行。

验证点：硬件根据 PSW.IS 决定是否加载 ISP，而不是根据 A10 的地址判断它属于 USTACK 还是 ISTACK。

18. 栈与 CSA 的容量预算思路

18.1 CSA 预算

CSA 数量至少要覆盖同时存在的：

任务普通 CALL 深度
+ IRQ/Trap 自动 Upper Context
+ BISR/SVLCX Lower Context
+ ISR/Trap 内部 CALL 深度
+ 最大异常嵌套深度
+ FCD 与异步 Trap 安全余量
+ RTOS 非运行任务保留的 CSA Call Chain

不能只按“任务数量 × 一个 CSA”估算。

18.2 ISTACK 预算

ISTACK 主要覆盖：

  • ISR/Trap 局部变量；
  • 编译器 spill；
  • 栈传参；
  • FCALL 保存的返回地址；
  • 同核最大异常嵌套路径；
  • Handler 调用的普通函数栈开销。

Upper/Lower 寄存器大部分进入 CSA，并不意味着 ISTACK 可以设置得很小。大型局部数组、深层 C 调用和库函数仍可能快速消耗 ISTACK。

18.3 USTACK 预算

每个任务自己的 USTACK 覆盖：

  • 任务普通函数局部变量；
  • 普通函数栈传参；
  • spill 与临时对象；
  • FCALL/FRET 开销；
  • 任务最深普通调用路径。

如果 IRQ 正常切换到 ISTACK，ISR 的普通栈开销不会继续消耗被中断任务的 USTACK；这正是独立 ISTACK 的重要价值。

19. 常见误区快速纠正

误区 1：CSA 就是 TriCore 的栈

不准确。CSA 是寄存器上下文存储池；A10 指向的普通 RAM 才是 C 语言意义上的栈。

误区 2：ISP 会随着 ISR 压栈实时变化

不准确。普通栈操作改变的是 A10；ISP 通常保持为 ISTACK 入口值。

误区 3：PSW.IS=1 会立即切换到 ISP

不准确。PSW.IS 是异常入口判断条件；单独修改它不会自动执行 A10=ISP。

误区 4：每一层嵌套中断都会重新从 ISTACK_TOP 开始

不准确。只有从 IS=0 首次进入异常时才加载 ISP；嵌套异常在当前 A10 上继续使用 ISTACK。

误区 5：IRQ 已经自动保存全部寄存器

不准确。IRQ 自动保存 Upper Context；Lower Context 要按需用 BISR/SVLCX 保存。

误区 6：FCD 说明当前上下文保存失败

不准确。FCD 发生时当前保存已经完成；FCU 才表示无法完成保存并造成状态丢失。

误区 7：AURIX ISP 等于 M7 MSP

不准确。MSP 是持续变化的独立活动 SP；AURIX ISP 主要是首次异常切栈时装入 A10 的源值。

误区 8：A10 栈扫描就能还原完整 Call Stack

不准确。普通 CALL 的 Upper Context 位于 CSA 链，还要结合 A11、PCXI 和调试展开信息。

20. 最后形成的系统认知

32 个 GPR
├── Global：A0、A1、A8、A9
├── Lower：A2～A7、D0～D7，加 A11、PCXI 形成 Lower Context
└── Upper：A10～A15、D8～D15，加 PSW、PCXI 形成 Upper Context

普通内存栈
└── 当前活动指针：A10

异常栈切换
├── ISP：首次异常切换时提供 ISTACK 入口值
└── PSW.IS：记录当前执行流采用的栈类别

CSA 管理
├── FCX：空闲 CSA 链头
├── PCXI.PCX：已使用上下文链头
├── PCXI.UL：链头是 Upper 还是 Lower
└── LCX：接近耗尽预警点

20.1 普通函数调用

CALL：Upper → CSA，A11 ← return address
函数局部数据：A10 指向的当前普通栈
RET：Upper ← CSA，CSA 回到 Free List

20.2 中断或 Trap

入口：Upper → CSA
若旧 IS=0：A10 ← ISP
PSW.IS ← 1
必要时：BISR/SVLCX 保存 Lower
返回前：RSLCX 恢复 Lower
RFE：恢复 Upper、A10、PSW.IS、IE、CCPN

20.3 和 M7 的一句话区别

Cortex-M7：MSP 与 PSP 是两个独立、持续存在的栈指针；异常基本帧压入异常前活动栈。

AURIX：A10 是唯一当前活动 SP；异常寄存器现场主要进入 CSA，ISP 只在首次异常切栈时装入 A10。

21. 自测题

  1. 为什么 A10 同时出现在 Upper CSA 中，又继续作为被调用函数的 SP？
  2. 为什么 A11 同时出现在 Upper 和 Lower Context？
  3. 如果 PCXI.UL=0 时执行 RFE，会发生什么？
  4. 为什么第二层 IRQ 不能重新执行 A10=ISP？
  5. FCD 与 FCU 对系统可恢复性的差异是什么？
  6. 一个 ISR 执行 BISR 后又调用两层普通函数，峰值额外需要多少个 CSA？
  7. 为什么直接扫描 A10 指向的内存不能完整回溯 TriCore 调用链？
  8. PSW.IS=1 能否证明 A10 一定落在 ISTACK 地址范围？
  9. 为什么软件读取活动 CSA 前要执行 DSYNC？
  10. Cortex-M7 Thread 使用 PSP 时，异常基本帧和 Handler 局部变量分别通常放在哪里？

参考答案要点

  1. CALL 先保存调用者 A10；被调用函数随后继续使用当前任务同一普通栈，编译器可再调整 A10。
  2. Upper 保存被打断/调用者的返回链；Lower 保存显式保护时当前 Handler 的返回链。
  3. RFE 期待 Upper Context，类型不匹配触发 CTYP。
  4. 会覆盖外层 ISR 已经使用的 ISTACK 内容。
  5. FCD 本次保存已完成，是预警；FCU 保存失败且状态丢失，通常不可恢复。
  6. IRQ Upper 1 个 + BISR Lower 1 个 + 两层 CALL Upper 2 个，共峰值 4 个；若只问 BISR 后两层 CALL 的新增量，则再增加 2 个。
  7. 普通 CALL 的 Upper Context 和返回链在 CSA 中，另外还可能存在 FCALL 栈记录与调试展开规则。
  8. 不能；硬件不会根据 A10 地址自动校验 PSW.IS。
  9. 实现可能缓冲活动 CSA 状态，DSYNC 使其提交到内存。
  10. 基本帧压入 PSP 指向的任务栈；进入 Handler 后，Handler 局部变量通常使用 MSP。

23. 阅读后的下一步建议

按下面顺序实操最容易真正建立直觉：

  1. 先单步一个普通 CALL/RET，观察一个 Upper CSA 的分配与回收；
  2. 再观察从 IS=0 的任务进入第一层 IRQ，确认 A10 从 USTACK 切到 ISP；
  3. 在 ISR 中加入 BISR/RSLCX，观察 PCXI.UL 在 1 → 0 → 1 间变化；
  4. 最后做一次两级嵌套中断，确认内层 IRQ 没有重新加载 ISP。

做完这四个实验后，再阅读 RTOS Task Context Switch，会比直接从 OS 汇编入口读起清楚得多。
