左侧是 C 源码，右侧是 TASKING 编译器在 -O0 下生成的汇编（.src）。 .Lxxx 是编译器内部标签，不是源码符号。函数入口地址来自 ELF 符号表（readelf -sW），大小来自符号的 size 字段。

先建立 5 条设计直觉（为什么启动代码长这样）

  1. 先有资源，再进 C：CSA 空闲链表 → 向量表/ISP → C 运行时。在此之前不能安全地调用普通 C 函数——调用会写 A11、消费 CSA，而池子可能还没建好。
  2. 能不调用就不调用：启动阶段大量使用 IFX_SSW_INLINE/宏/内联汇编；TASKING 的 #pragma optimize R 也是为减少不必要的栈使用。看懂这一点，就不会问“为什么这些函数都看不见”。
  3. 尾跳转用 ji，需要返回才用 jli/call：阶段之间是单向的；用 call 会白占 CSA，返回地址也没有意义。
  4. 分阶段是因为“复位类型”不同：上电需要 PMS/EVRC/时钟/自检；应用复位假设电源/时钟已稳定，跳过这些步骤。
  5. 每一步都在为下一步准备前提：PSW 给已知状态 → CSA 给上下文池 → BTV/BIV/ISP 给异常/中断 → 最后才 enable 中断、进 core0_main。

1_START — 复位入口

入口地址 0xA0000000 大小 12 B 源码 Ifx_Ssw_Tc0.c:358–361

CPU 复位后从 0xA0000000 取第一条指令。这里只做一件事：跳到 __StartUpSoftware。

先想一想 · 自己回答后再展开
Q1_START 为什么用 ji，而不是 call / jli？
提示：先想：call 比 ji 多做了什么？_START 之后还需要回来吗？
call/jli 会把返回地址写入 A11，并可能消费一个 CSA；_START 是复位入口，没有调用者，也永远不返回，所以用 ji（尾跳转）。工程里 Ifx_Ssw_jumpToFunction 展开就是 ji，而 Ifx_Ssw_jumpToFunctionWithLink 才是 jli——函数命名已经说明了区别。
Q2既然 ji 不会返回，编译器为什么还生成 ret？
提示：看 C 函数签名：void _START(void)。编译器是否知道 ji 永不返回？
编译器按普通 void 函数生成返回路径；ji 之后不可达，ret 是死代码。若想省掉，可把函数标注为 noreturn，但复位入口的 12 字节里多一条 ret 无伤大雅。
Q3为什么 _START 位于 0xA0000000，而不是 0x80000000？
提示：看 map 的 Locate Result：reset 段放在 pfls0，但地址是 0xA0000000。
0xA0000000 是 PFlash0 的非缓存别名。复位时缓存尚未配置，从非缓存别名取指可以避免缓存初始化/一致性问题；跳转后的代码再进入缓存别名区。具体定位由 LSL 的 start/reset 段决定。
Q4为什么不让 _START 直接内联 __StartUpSoftware 的全部代码？
提示：复位入口段有多大？它受什么保护？
复位入口只需要一条可靠的跳转；start/reset 段很小且受保护（#pragma protect on），把完整启动逻辑放在普通代码段更利于链接、调试和保护。

举一反三 · 跨架构 / 跨层对照
  • Cortex-M：复位向量表项给出初始 MSP 和 Reset_Handler 地址，CPU 取向量后跳转；TriCore：固定地址 0xA0000000 放的是可执行指令，第一条指令自己完成跳转。

  • 把 ji 改成 call：多消费一个 CSA，且 ret 会回到复位向量，形成无意义循环。

  • `#pragma section code "start"` + `#pragma protect on` 把复位入口放到受保护段。

2__StartUpSoftware — 建立最小运行环境

入口地址 0x80003CDC 大小 144 B 源码 Ifx_Ssw_Tc0.c:132–149

设置小数据基址 A1、把 PSW 复位到已知值、判断本次复位类型，然后分流到上电复位路径或应用复位路径。

先想一想 · 自己回答后再展开
Q1为什么先设置 PSW，再去判断复位类型？
提示：warm reset 后 PSW 可能残留哪些位？判断逻辑依赖这些位吗？
为了保证后续代码在已知状态下运行（GW/IS/IO 等位），避免 warm reset 残留状态影响判断与栈行为。先把 PSW 归到默认值，再谈分支。
Q2mtcr PSW 之后为什么必须 isync？
提示：CSFR 写入是否像普通寄存器一样立即对后续指令可见？
CSFR 写入是流水线化的；isync 等待其生效，确保后续指令看到新的 PSW（尤其是 IS/IE 等控制位）。PSW 位域见下方“背景 1”。
Q3为什么用 movh.a + lea 取地址，而不是从内存加载一个 32 位常量？
提示：TriCore 指令里有没有 32 位立即数？@his/@los 是谁分配的？
TriCore 没有 32 位立即数寻址；movh.a 装高 16 位、lea 补低 16 位，链接器用 @his/@los 重定位。这样不需要额外数据访存，也不依赖文字池。
Q4复位类型判断为什么要用 clz / extr.u，而不是直接比较 RSTSTAT？
提示：RSTSTAT 是“一个复位源”还是“一组复位源的位图”？RSTCON 的配置是几位？
RSTSTAT 是位图，可能多个源同时置位。链条是：clz 数前导零 → 31-clz = 最高置位位的位号 → 左移 1 位得到 RSTCON 中该复位源的 2-bit 字段偏移 → extr.u 取这 2 bit；等于 2 表示应用复位。这就是 clz/rsub/sh/extr.u 四条指令的分工。
Q50x980 里 PSW.IS 是 0 还是 1？如果搞反了会怎样？
提示：PSW.IS 是 bit 9；0x980 = 0x800 + 0x100 + 0x80。
IS=0（C 注释也写的是 clear PSW.IS）。0x980 的完整位域见下方“背景 1”。如果误以为 IS=1，会错误理解首次中断是否切栈——IS=0 表示当前不在中断栈上，下一次中断硬件会切到 ISP 并把 IS 置 1。
Q6mtcr #65028,d15 里的 65028 是什么？
提示：把 65028 转成十六进制，再查 CSFR 地址表。
65028₁₀ = 0xFE04 = CPU_PSW 的 CSFR 地址。mtcr 的第一个操作数是 CSFR 地址，汇编器在 .src 里用十进制打印；同类还有 65080=FCX、65084=LCX、65060=BTV 等（见背景 2 的换算表）。

0x980 = 0x800 + 0x100 + 0x80：CDE=1、GW=1、IO=10（Supervisor），其余为 0，特别是 IS=0。每一项都有用途：
• GW=1：后面 __Core0_start 还要写 A0/A1/A8/A9；GW=0 时这些全局地址寄存器写入会被禁止。
• IO=10：I/O 处于 Supervisor（全部权限），才能执行 mtcr、访问 CSFR 和外设。
• CDE=1 / CDC=0：开启调用深度计数，上限 64，用于尽早发现失控的调用深度。
• IS=0：当前不在中断栈；下一次中断硬件会切到 ISP 并把 IS 置 1——这正是 C 注释 “clear PSW.IS” 的含义。
• S=0：这是 PSW Safety 位（来自 SYSCON），不是“Supervisor”位；别把 S 和 IO 搞混。

背景 2：mtcr #65028 的 65028 是什么

3Phase2 — 电源/EVRC 初始化（仅上电路径）

入口地址 0x80003D6C 大小 36 B 源码 Ifx_Ssw_Tc0.c:152–164

上电复位才需要：初始化 PMSM/EVRC，跑 LBIST/MONBIST（本配置为空），然后进入 Phase3 的 CSA 初始化。

先想一想 · 自己回答后再展开
Q1为什么 PMS 初始化用 jli（带链接），而阶段切换用 ji？
提示：PMS 初始化之后还要继续执行吗？阶段切换之后还要回来吗？
PMS 初始化是普通调用，返回后继续跑 Phase2 的后续语句；阶段切换是尾跳转，永远不回来。jli 会写 A11/可能消费 CSA，ji 不会。
Q2为什么 LBIST/MONBIST 在汇编里完全看不到？
提示：看 C 里的 IFX_CFG_SSW_CALLOUT_LBIST() 宏在本工程配置下展开成什么。
callout 在本工程配置为空（开发构建跳过自检）；生产/安全构建应启用。读启动代码时必须同时看配置宏，否则会误以为“漏了”。
Q3上电复位和应用复位为什么走不同的 Phase3 入口？
提示：上电时电源、时钟、PLL 一定已经稳定吗？应用复位时呢？
上电路径需要 PMS/EVRC/LBIST 等完整初始化；应用复位通常假设电源与时钟已稳定，跳过这些步骤直接进入后续阶段。

IFX_SSW_INIT_CONTEXT() 被完全内联展开。它把 __CSA0..__CSA0_END 这 0x2000 字节（128 个 64B CSA）串成一条空闲链表，FCX 指向表头，LCX 指向接近表尾的位置。

先想一想 · 自己回答后再展开
Q1CSA 空闲链表为什么必须由软件建立，硬件不能自己建？
提示：硬件在 CALL/中断时从 FCX 取 CSA，在 RET/RFE 时归还；上电时 FCX 里有什么？
硬件只负责“取/还”，不负责“初始化池子”。首次上电时 FCX 没有有效链表，必须由软件把 CSA 区串成单链表一次；之后硬件才能正常 pop/push。
Q2为什么每块 CSA 是 64 字节？
提示：Upper Context 和 Lower Context 各多少个字？每个字几字节？
Upper 16 字 + Lower 16 字，每字 4 字节 = 64 字节；这是 TriCore 硬件固定的 CSA 格式。
Q3为什么 LCX 指向倒数第 3 块，而不是最后一块？
提示：LCX 是“耗尽点”还是“预警点”？留余量有什么好处？
LCX 是接近耗尽的警戒线；留几块余量，让硬件在真正耗尽前触发 FCD，软件还有机会处理。具体阈值由硬件/软件约定，本工程按 count-3 设置。
Q4循环里为什么既要有 dsync 又要有 isync？
提示：dsync 管什么？isync 管什么？FCX/LCX 是内存还是 CSFR？
dsync 保证 CSA 链表的普通内存写入对硬件可见；isync 保证 FCX/LCX 这些 CSFR 写入在后续取指前生效。两者管的层次不同。
Q5如果 FCX 没初始化就调用 pxPortInitialiseStack，会发生什么？
提示：port.c 里领 CSA 的第一步是什么？拿到无效值会怎样？
会从无效 FCX 取 CSA，可能触发 FCD/trap，或把任务上下文写到非法内存，导致任务创建失败/系统崩溃。
Q6为什么在循环前就把 A10 设为 __USTACK0？
提示：此时中断可能还没开，但 trap 会不会发生？启动代码需不需要一个有效栈？
给启动代码和潜在 trap 一个有效用户栈；即使中断关闭，trap（如访问错误）仍可能发生。

Q2为什么 xTaskCreate 必须在 vTaskStartScheduler 之前？

Q3xTaskCreate 的 6 个参数分别落在哪些寄存器？为什么？

Q4为什么 vTaskStartScheduler 不返回？
提示：调度器启动后，CPU 的上下文切到谁？main 的调用栈还在吗？
它恢复第一个任务的上下文（CSA/PCXI），CPU 从此在任务里运行；main 的上下文被放弃，所以不会返回。
Q5如果先启动调度器再创建任务，会怎样？
提示：FreeRTOS 的断言/文档对这种情况怎么说？
违反 API 使用约束，行为未定义或触发断言；正确做法是在启动前创建，或在任务中动态创建。
Q6configMINIMAL_STACK_SIZE = 256 words 够不够？

对简单 LED 任务通常够；用 uxTaskGetStackHighWaterMark 实测水位，S4 内存阶段会做。
