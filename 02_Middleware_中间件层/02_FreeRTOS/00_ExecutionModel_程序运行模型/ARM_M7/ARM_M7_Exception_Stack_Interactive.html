01M7 运行模型总图

Cortex-M7 的程序运行模型可以压成一句话：硬件自动压栈 + EXC_RETURN 返回 + 双栈 + NVIC。先建立总图，后面每一节只拆其中一块。

Thread Mode（PSP）：任务代码运行在这里。FreeRTOS 让每个任务使用自己的 PSP；异常入口把现场压到任务栈上，Handler 改用 MSP。

硬件保存什么？

R0–R3、R12、LR、PC、xPSR 由硬件自动压栈；R4–R11 由软件（PendSV）保存。

返回靠什么？

不是普通函数返回，而是 BX LR，LR 里是 EXC_RETURN，告诉硬件回 Thread/Handler、用 MSP/PSP、是否带 FPU。

和 TriCore 的一句话区别

TriCore 把上下文挂在 CSA 链上；M7 把异常现场压在执行栈上。一个是链表，一个是栈帧。

先想一想

为什么 M7 的异常入口只自动保存 8 个寄存器，而不是把 R0–R15 全部保存？

提示

因为 AAPCS 已经规定 R0–R3、R12 是调用者保存寄存器；异常入口相当于一次“硬件发起的函数调用”，只保存调用者可能还需要的现场。R4–R11 是 callee-saved，由被调用的上下文（FreeRTOS 的 PendSV）负责。

举一反三

看到“硬件自动压栈”时，顺手问三个问题：压到哪条栈？压几个字？返回时谁把 SP 加回去？这三个问题会贯穿第 3、4、6 节。

02寄存器与模式

M7 的寄存器不多，但要分清三类：通用寄存器、特殊寄存器、以及只影响中断屏蔽的 mask 寄存器。点击任意寄存器查看它在异常/上下文切换中的角色。

程序员可见寄存器

点击一个寄存器。说明会显示：它是什么、谁保存、在 FreeRTOS 切换时是否重要。

xPSR 的三个部分

部分位作用
APSR31–27N/Z/C/V/Q 条件标志
IPSR8–0当前异常号；0 = Thread Mode
EPSR24 / 9T 位（Thumb）、栈对齐位 bit9

异常栈帧里的 xPSR 包含 IPSR 与对齐位；调试器里看到的 xPSR 可能是 0x01000000（只有 T 位）。

CONTROL：三颗开关

CONTROL 只有在特权级才能写；非特权任务想改，必须先通过 SVC 陷入内核。

先想一想

为什么 FreeRTOS 不把任务栈指针放在 R13，而是让任务使用 PSP？

提示

因为 Handler Mode 永远用 MSP。如果任务也用 MSP，异常一进入就会覆盖任务栈；双栈把“任务栈”和“异常/内核栈”物理分开，嵌套中断也不会踩到任务栈。

03双栈与权限

M7 有两条栈指针：MSP 和 PSP。Handler Mode 永远用 MSP；Thread Mode 用哪条，由 CONTROL.SPSEL 决定。把这三个开关拨一遍，观察当前栈和可执行动作。

模式 权限 Thread 栈选择

MSP

Main Stack Pointer

复位后默认栈；Handler Mode 强制使用。

PSP

Process Stack Pointer

Thread Mode 可选；FreeRTOS 任务栈使用它。

当前：Thread / Privileged / MSP。任务如果用 MSP，异常入口会压到同一栈上。

FreeRTOS 的用法

  • 任务：Thread Mode + PSP，每个任务一条栈。
  • 异常/内核：Handler Mode + MSP。
  • 首次启动：SVC 从任务栈恢复 PSP，然后返回 Thread/PSP。

权限边界

  • 非特权不能写 CONTROL、NVIC、SCB 等系统寄存器。
  • 非特权可以执行 SVC，主动请求内核服务。
  • MPU 可以把任务栈/外设划成非特权不可写。
先想一想

Handler Mode 下把 CONTROL.SPSEL 置 1，Thread 返回时会用哪条栈？

提示

SPSEL 只影响 Thread Mode；Handler Mode 仍用 MSP。异常返回时，EXC_RETURN 的 bit2 决定回 Thread 用 MSP 还是 PSP，和 Handler 期间 SPSEL 的值不是一回事。

04异常入口与硬件栈帧

异常入口是 M7 运行模型的核心：硬件自动把 8 个字压到当前栈上。点“触发异常”，一步一步看 SP 怎么下降、帧怎么长出来；再打开 FPU，看扩展帧和 lazy stacking。

SP = 0x20008000（异常前）
异常前：Thread Mode，PSP 指向任务栈顶。点“触发异常”开始压栈。
谁保存寄存器
硬件R0–R3、R12、LR、PC、xPSR
软件（PendSV）R4–R11；FPU 时另有 S16–S31
硬件（FPU 扩展帧）S0–S15、FPSCR、保留字

为什么是 8 个字？

AAPCS 把 R0–R3、R12 定为调用者保存；LR/PC/xPSR 是返回现场。R4–R11 是 callee-saved，留给软件保存。这样硬件帧最小，异常延迟低。

8 字节对齐

异常入口要求栈帧 8 字节对齐；如果 SP 不满足，硬件插入填充字，并在 xPSR bit9 标记。返回时按这个位恢复。

举一反三

FreeRTOS 的 pxPortInitialiseStack 构造的不是 8 字硬件帧，而是 17 字：8 字硬件帧 + 1 字 EXC_RETURN + 8 字 R4–R11。为什么多一个 EXC_RETURN？因为 PendSV 用 ldmia r0!, {r4-r11, r14} 把返回信息也放在任务栈上。第 8 节先看三个 API 的公共程序流（平台无关），第 9 节把 port 层抽象成必须履行的契约，第 10 节才落到 M7 的 xPortStartScheduler 和 SVC。

先想一想

如果任务正在用 FPU，异常入口压的是 8 字还是 26 字？什么时候压 26 字？

提示

FPU 活跃时是 26 字（8 字基本帧 + 18 字扩展帧）。如果开了 lazy stacking，异常入口先只保留空间，等第一次 FPU 指令再写入 S0–S15/FPSCR；这就是第 5 节。

05FPU 扩展帧与 lazy stacking

M7 的 FPU 让异常帧从 8 字变成 26 字。lazy stacking 的目的不是“省寄存器”，而是“没用到 FPU 的任务不为它付栈空间和写入成本”。

FPU 未使用：异常帧 8 字（32 B），栈里没有 S0–S15/FPSCR。
场景帧大小
基本帧8 字 = 32 B
FPU 扩展帧26 字 = 104 B
扩展部分S0–S15 + FPSCR + 保留字 = 18 字

三个关键位

  • CONTROL.FPCA：任务是否使用过 FPU。
  • FPCCR.ASPEN：异常入口是否自动保留 FPU 空间。
  • FPCCR.LSPEN：是否启用 lazy stacking。

和 FreeRTOS 的关系

V10.5.1 的 pxPortInitialiseStack 不会预填 S16–S31；初始 EXC_RETURN=0xFFFFFFFD（无 FPU）。第一次 FPU 指令后，硬件才把 FPU 上下文纳入异常帧。任务栈预算要按 104 B 的扩展帧留余量。

写错会怎样

把任务栈按 32 B 帧估算，但任务实际用了 FPU：中断嵌套几层后栈溢出，表现可能是 HardFault、任务数据被踩、或“随机”复位。栈预算必须按最坏路径算。

先想一想

lazy stacking 开启后，异常入口还会写 S0–S15 吗？什么时候写？

提示

入口只保留空间，不立即写；第一次 FPU 指令触发写回。若任务一直不用 FPU，这部分空间就一直是保留状态。

06EXC_RETURN 与异常返回

异常返回不是普通 BX LR：LR 里装的是 EXC_RETURN，低 4 位告诉硬件“回哪个模式、用哪条栈、有没有 FPU 帧”。点不同值看解码。

先想一想

为什么 EXC_RETURN 的低 4 位不是普通地址的一部分？

提示

因为异常返回地址在栈帧的 PC 里；EXC_RETURN 是给硬件解码的控制字。低 4 位的组合表示模式/栈/FPU，不是跳转地址。

07NVIC、向量表、优先级、尾链

NVIC 决定“谁先跑、能不能打断、结束后要不要出栈再入栈”。M7 的优先级是数值越小越高；FreeRTOS 的临界区用 BASEPRI 只屏蔽一部分中断。

先想一想

为什么 FreeRTOS 的临界区用 BASEPRI，而不是 PRIMASK？

提示

PRIMASK 屏蔽所有可配置中断，会让高优先级中断也延迟；BASEPRI 只屏蔽“优先级数值 ≥ 阈值”的中断，保留高优先级（数值更小）中断的实时性。阈值就是 configMAX_SYSCALL_INTERRUPT_PRIORITY。

08公共程序流：两个任务 + 启动调度器

这一节只看 FreeRTOS 公共层：两次 xTaskCreate、一次 vTaskStartScheduler。它们不知道底下是 M7 还是 TriCore；讲到 xPortStartScheduler() 这个平台分界点就停。每个关键结论都给源码位置；最后会看到 timer task 如何在启动前改写 pxCurrentTCB。

你实际写的三行

xTaskCreate(task_app_led1, "APP LED1", configMINIMAL_STACK_SIZE, NULL, 1, NULL);
xTaskCreate(task_app_led2, "APP LED2", configMINIMAL_STACK_SIZE, NULL, 1, NULL);
vTaskStartScheduler();

栈

configMINIMAL_STACK_SIZE = 256 字 → 1 KB/任务；xTaskCreate 的 usStackDepth 单位是 StackType_t，不是字节。

优先级

两个 LED 任务都是 1；idle 是 0；timer task 是 configTIMER_TASK_PRIORITY = 9（本工程最高）。

节拍

configTICK_RATE_HZ = 1000 → 1 tick = 1 ms；250/500 就是 250/500 tick。

源码证据：xTaskCreate 到底做了什么

位置：tasks.c 的 xTaskCreate（L721）、prvInitialiseNewTask（L816）、prvAddNewTaskToReadyList（L1026）。

/* 只保留关键路径，省略错误处理/条件编译 */
pxStack = pvPortMallocStack( usStackDepth * sizeof( StackType_t ) );
pxNewTCB = ( TCB_t * ) pvPortMalloc( sizeof( TCB_t ) );
memset( pxNewTCB, 0x00, sizeof( TCB_t ) );
pxNewTCB->pxStack = pxStack;
prvInitialiseNewTask( pxTaskCode, pcName, usStackDepth, pvParameters,
                      uxPriority, pxCreatedTask, pxNewTCB, NULL );
prvAddNewTaskToReadyList( pxNewTCB );
return pdPASS; /* 失败时返回 errCOULD_NOT_ALLOCATE_REQUIRED_MEMORY */
阶段实际动作为什么重要
分配先分配栈，再分配 TCB（portSTACK_GROWTH < 0）；TCB 清零栈向下长，先分配栈可避免栈长进 TCB；清零避免未初始化字段
初始化prvInitialiseNewTask：填 TCB 字段、算栈顶、调用 pxPortInitialiseStackTCB 第一成员必须是 pxTopOfStack；初始帧必须和真实异常帧一致
入就绪表prvAddNewTaskToReadyList：临界区、uxCurrentNumberOfTasks++、选择 pxCurrentTCB、插入 Ready 表调度器启动前，这里决定 pxCurrentTCB；timer task 创建时会把 LED 任务替换掉

TCB 里真正被初始化的字段

  • pxTopOfStack：必须是 TCB 第一成员；指向任务栈顶，PendSV/首任务恢复时从这里取。
  • xStateListItem / xEventListItem：任务状态表/事件表的链表节点；前者 Owner 指回 TCB，后者 Value = configMAX_PRIORITIES - priority。
  • uxPriority / uxBasePriority：调度优先级；有 mutex 时还要记 base priority。
  • pxStack / pcTaskName：栈基址、调试名；栈溢出检查和调试器靠它们。
  • uxCriticalNesting（若 portCRITICAL_NESTING_IN_TCB）：临界区嵌套计数；port 可能放在 TCB，也可能放在 port 自己的全局变量里。

pxCurrentTCB 的选择：源码里的 <=

if( pxCurrentTCB == NULL ) {
    pxCurrentTCB = pxNewTCB;
} else if( xSchedulerRunning == pdFALSE ) {
    if( pxCurrentTCB->uxPriority <= pxNewTCB->uxPriority ) {
        pxCurrentTCB = pxNewTCB;
    }
}

因为条件用的是 <=，同优先级时后创建的任务也会替换当前任务。你的工程里 LED1 先创建、LED2 后创建，都是 priority 1，所以 LED2 先成为 pxCurrentTCB。但 vTaskStartScheduler 随后创建 timer task（priority 9），它再次替换 pxCurrentTCB；最终首任务是 Tmr Svc。它阻塞到定时器队列后，PendSV 才切到 LED2。

vTaskStartScheduler：公共层最后一步

位置：tasks.c L1954。

  1. 创建 idle 任务（priority 0）；若 configUSE_TIMERS=1，再创建 timer task（priority = configTIMER_TASK_PRIORITY = 9），它会成为最高优先级就绪任务。
  2. portDISABLE_INTERRUPTS()：确保 tick 不会在启动过程中打断。
  3. 设置 xSchedulerRunning = pdTRUE、xTickCount = 0、xNextTaskUnblockTime = portMAX_DELAY。
  4. 调用 xPortStartScheduler()；正常不返回。只有 port 启动失败或应用调用 vTaskEndScheduler() 才可能返回。

先想一想

如果只看 LED 任务，LED2 先跑；但整个系统的第一个任务为什么是 Tmr Svc？

提示

vTaskStartScheduler 先建 idle（0），再建 timer task（configTIMER_TASK_PRIORITY = 9）。9 > 1，prvAddNewTaskToReadyList 的 <= 比较会把 pxCurrentTCB 换成 Tmr Svc。Tmr Svc 阻塞到定时器队列后，PendSV 才切到 LED2。

举一反三

公共层只负责“选哪个任务”；怎么保存、怎么切、怎么产生 tick 都是 port 层的事。下一节把 port 层当成接口，问“任何平台都必须做什么”。

09抽象 port 契约：xPortStartScheduler() 必须做什么

这一节不出现 SVC、PendSV、SysTick，也不出现 MSP/PSP。只回答一个问题：任何平台的 xPortStartScheduler() 必须保证什么？ 为什么这些事内核公共代码不能自己做？

公共内核知道“该跑哪个任务”，但不知道“怎么让 CPU 跑起来”。port 层就是这两者之间的适配层。

六条职责与不变量

职责必须保证什么（不变量）内核为什么不能自己做违反后果
1. 周期 tick 按 configTICK_RATE_HZ 产生周期中断；每次 tick 都让 xTaskIncrementTick 有机会执行；丢失的 tick 要能补记。 内核不知道定时器、时钟源、中断控制器。 vTaskDelay 永不到期、时间片停摆、tick 计数漂移。
2. 切换触发 提供一个可由任务/ISR 请求的切换机制；真正切换时保存当前上下文、调用 vTaskSwitchContext、恢复下一个任务；不能在临界区/调度器挂起时切。 内核不知道异常/陷阱/软件中断机制，也不知道寄存器保存方式。 taskYIELD/ISR yield 不生效；任务饿死；或在临界区切走导致链表损坏。
3. 首任务上下文 把 pxCurrentTCB->pxTopOfStack 变成 CPU 可执行状态；布局必须和 pxPortInitialiseStack 完全一致；返回模式/栈/FPU 状态必须正确。 内核不知道寄存器文件、栈帧格式、返回指令。 第一个任务直接 HardFault；返回错模式/错栈；FPU 上下文错乱。
4. 中断屏蔽/临界区 提供 portDISABLE_INTERRUPTS/portENABLE_INTERRUPTS 与临界区原语；屏蔽范围要符合内核的“最大系统调用优先级”约定，不能把高优先级中断也长期挡住。 内核不知道中断优先级寄存器/屏蔽位。 任务链表被 ISR 破坏；丢唤醒；高优先级中断延迟失控。
5. 启动首任务且不返回 把 CPU 交给 pxCurrentTCB；正常路径不返回 vTaskStartScheduler；返回只代表启动失败或主动结束调度。 内核没有“返回到 main”的调用约定；它只有任务上下文。 返回后跑 while(1)，任务永远不执行；调度器状态与硬件状态不一致。
6. 平台可选特性 按需初始化 FPU、MPU、cache、时钟、调试；必须与上下文布局和任务栈预算一致。 这些是平台/芯片特性，内核不可知。 FPU 帧大小估算错、MPU 拦掉任务栈、cache 一致性错误。

抽象伪代码

BaseType_t xPortStartScheduler( void )
{
    setup_tick_interrupt( configTICK_RATE_HZ );
    setup_context_switch_trigger();
    prepare_first_context( pxCurrentTCB->pxTopOfStack );
    setup_interrupt_mask_and_priorities();
    enable_interrupts();
    switch_to_first_task(); /* never returns */
    return pdFAIL;          /* unreachable */
}

这里故意用抽象名：具体平台可能用定时器中断、软件中断、异常返回、陷阱指令……名字下一节才出现。

五条契约不变量

  1. tick 不丢：每个硬件 tick 最终都要反映到内核 tick 计数。
  2. 切换不穿透临界区：调度器挂起/临界区内不得真正切换。
  3. 首帧可返回：首任务上下文必须和真实异常/中断帧同构。
  4. 启动不返回：正常路径下 vTaskStartScheduler 永不返回。
  5. 屏蔽范围匹配：临界区屏蔽范围必须与内核“可调用 FromISR API 的最高优先级”约定一致。
违反契约会怎样

只建 tick、不建切换触发：时间在走，任务不换，表现为“延迟到期但任务不恢复”。
切换触发优先级太高：它能打断内核临界区，链表/就绪表可能损坏。
首任务帧和 pxPortInitialiseStack 不一致：第一次返回就取错 PC/PSR/栈，直接 fault。
临界区屏蔽范围不对：该屏蔽的没屏蔽，链表被 ISR 改坏；不该屏蔽的屏蔽了，实时性崩。

先想一想

如果 tick 正常、切换触发也正常，但首任务上下文少了一个寄存器，最先坏的是哪一步？

提示

不是 tick，也不是切换，而是“第一次从 port 启动代码返回到任务”的那一步：PC/PSR/栈指针任一不对，CPU 会取错指令或进错误模式，通常直接 fault。首帧必须和真实异常帧同构，原因就在这里。

举一反三

换到任何 RTOS/任何架构，port 层都可以用这六条来审：时间源、切换触发、首上下文、临界区、启动不返回、平台特性。下一节看 M7 如何逐条履行。

10M7 实现：xPortStartScheduler + 首任务（SVC）

第 9 节的抽象契约在 M7 上逐条落地：周期 tick 用 SysTick，切换触发用 PendSV，首任务用 SVC + PSP，优先级用 NVIC，临界区用 BASEPRI。这一节先看 xPortStartScheduler 如何把这些配置好，再逐行走 prvPortStartFirstTask / vPortSVCHandler；首任务是第 8 节源码结论中的 Tmr Svc（timer task，priority 9）；它阻塞后 PendSV 才切到 LED2。

举一反三

为什么 SVC 的硬件帧在 MSP，而任务帧在 PSP？因为 svc 0 执行时还在 Thread/MSP；异常入口把 SVC 现场压到 MSP。Handler 里再把 PSP 指向任务栈，返回时 EXC_RETURN 指定 Thread/PSP，于是任务用自己的栈继续跑。

先想一想

ldmia r0!, {r4-r11, r14} 里的 r14 是什么？为什么不直接跳到任务函数？

提示

r14 是任务栈里的 EXC_RETURN（初始值 0xFFFFFFFD），不是普通返回地址。bx r14 让硬件执行异常返回流程：恢复 8 字硬件帧、切换 PSP、回到 Thread Mode。

11PendSV：真正的上下文切换

第 9 节说 port 必须提供“切换触发”；M7 选 PendSV。PendSV 是 FreeRTOS 的“切换开关”。异常入口已经把 R0–R3/R12/LR/PC/xPSR 压到任务栈；PendSV 只需要保存 R4–R11，再切换 PSP。点“下一步”看两个任务栈怎么交换。

; xPortPendSVHandler()
mrs r0, psp              ; 当前任务栈
ldr r3, =pxCurrentTCB
ldr r2, [r3]
tst r14, #0x10           ; FPU 上下文条件
vstmdbeq r0!, {s16-s31}
stmdb r0!, {r4-r11, r14} ; 软件保存
str r0, [r2]             ; 更新 TCB 栈顶
bl vTaskSwitchContext    ; 选下一个任务
ldr r1, [r3]
ldr r0, [r1]            ; 新任务栈顶
ldmia r0!, {r4-r11, r14}
msr psp, r0
bx r14                  ; EXC_RETURN
切换前：任务 A 正在运行，PendSV 已进入。硬件已把 A 的基本帧压到 A 的任务栈。

Task A

PSP_A

运行中 → 保存 R4–R11 → 栈顶写入 TCB_A。

Task B

PSP_B

就绪 → 从 TCB_B 取栈顶 → 恢复 R4–R11 → PSP_B。

PendSV 通常设为最低优先级，确保它不会打断高优先级中断；高优先级中断可以“迟到”并先执行。
举一反三

如果 PendSV 不是最低优先级，会发生什么？高优先级中断可能被切换流程延迟，实时性变差；更糟的是，PendSV 里调用 vTaskSwitchContext 时又被中断打断，栈/TCB 状态会变得难以推理。

先想一想

为什么 PendSV 保存 R4–R11，而不是 R0–R3？

提示

R0–R3、R12、LR、PC、xPSR 已在异常入口由硬件压栈；R4–R11 是 callee-saved，硬件不保存，必须由 PendSV 软件保存。两段合起来才是完整上下文。

12SysTick 与 tick

第 9 节说 port 必须提供周期 tick；M7 选 SysTick。SysTick 只做两件事：把 tick 加一，判断要不要切换。它不直接做上下文切换，而是“挂起 PendSV”，让 PendSV 在合适的时候完成切换。

tick = 0 PendSV: 未挂起
T0SysTick 异常进入，Handler 使用 MSP
T1xPortSysTickHandler 调 xTaskIncrementTick
T2如果返回 pdTRUE，portYIELD_FROM_ISR 写 ICSR bit28
T3PendSV 挂起；SysTick 返回
T4PendSV 执行，完成上下文切换
tick=0：点“来一个 SysTick”。

关键寄存器/位

  • SysTick->CTRL/LOAD/VAL：tick 时基。
  • SCB->ICSR bit28：PendSV set。
  • portNVIC_PENDSVSET_BIT = 1 << 28。

为什么不直接在 SysTick 里切？

SysTick 可能和其他中断嵌套；把切换推迟到最低优先级的 PendSV，可以保证所有高优先级中断先处理完，切换时序更可控。

先想一想

如果 xTaskIncrementTick 返回 pdFALSE，还会进 PendSV 吗？

提示

不会主动挂起；只有需要切换时才写 ICSR bit28。但 PendSV 可能因为其他原因已经挂起，不能只看 SysTick。

防跑偏三件事

1）不要把 x86 的调用栈直觉直接套到 M7：异常入口是硬件压栈，返回靠 EXC_RETURN。
2）不要混“硬件保存”和“软件保存”：R0–R3/R12/LR/PC/xPSR 是硬件；R4–R11 是 PendSV。
3）不要把 FreeRTOS 的 17 字初始帧当成 8 字硬件帧：多出来的是 EXC_RETURN + R4–R11。
