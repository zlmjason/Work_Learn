01M7 运行模型总图

Cortex-M7 的程序运行模型可以压成一句话：硬件自动压栈 + EXC_RETURN 返回 + 双栈 + NVIC。先建立总图，后面每一节只拆其中一块。

Thread Mode（PSP）：任务代码运行在这里。FreeRTOS 让每个任务使用自己的 PSP；异常入口把现场压到任务栈上，Handler 改用 MSP。

硬件保存什么？

R0–R3、R12、LR、PC、xPSR 由硬件自动压栈；R4–R11 由软件（PendSV）保存。

返回靠什么？

不是普通函数返回，而是 BX LR，LR 里是 EXC_RETURN，告诉硬件回 Thread/Handler、用 MSP/PSP、是否带 FPU。

和 TriCore 的一句话区别

TriCore 把上下文挂在 CSA 链上；M7 把异常现场压在执行栈上。一个是链表，一个是栈帧。

先想一想

为什么 M7 的异常入口只自动保存 8 个寄存器，而不是把 R0–R15 全部保存？

提示

因为 AAPCS 已经规定 R0–R3、R12 是调用者保存寄存器；异常入口相当于一次“硬件发起的函数调用”，只保存调用者可能还需要的现场。R4–R11 是 callee-saved，由被调用的上下文（FreeRTOS 的 PendSV）负责。

举一反三

看到“硬件自动压栈”时，顺手问三个问题：压到哪条栈？压几个字？返回时谁把 SP 加回去？这三个问题会贯穿第 3、4、6 节。

02寄存器与模式

M7 的寄存器不多，但要分清三类：通用寄存器、特殊寄存器、以及只影响中断屏蔽的 mask 寄存器。点击任意寄存器查看它在异常/上下文切换中的角色。

程序员可见寄存器

点击一个寄存器。说明会显示：它是什么、谁保存、在 FreeRTOS 切换时是否重要。

xPSR 的三个部分

部分位作用
APSR31–27N/Z/C/V/Q 条件标志
IPSR8–0当前异常号；0 = Thread Mode
EPSR24 / 9T 位（Thumb）、栈对齐位 bit9

异常栈帧里的 xPSR 包含 IPSR 与对齐位；调试器里看到的 xPSR 可能是 0x01000000（只有 T 位）。

CONTROL：三颗开关

CONTROL 只有在特权级才能写；非特权任务想改，必须先通过 SVC 陷入内核。

先想一想

为什么 FreeRTOS 不把任务栈指针放在 R13，而是让任务使用 PSP？

提示

因为 Handler Mode 永远用 MSP。如果任务也用 MSP，异常一进入就会覆盖任务栈；双栈把“任务栈”和“异常/内核栈”物理分开，嵌套中断也不会踩到任务栈。

03双栈与权限

M7 有两条栈指针：MSP 和 PSP。Handler Mode 永远用 MSP；Thread Mode 用哪条，由 CONTROL.SPSEL 决定。把这三个开关拨一遍，观察当前栈和可执行动作。

模式 权限 Thread 栈选择

MSP

Main Stack Pointer

复位后默认栈；Handler Mode 强制使用。

PSP

Process Stack Pointer

Thread Mode 可选；FreeRTOS 任务栈使用它。

当前：Thread / Privileged / MSP。任务如果用 MSP，异常入口会压到同一栈上。

FreeRTOS 的用法

  • 任务：Thread Mode + PSP，每个任务一条栈。
  • 异常/内核：Handler Mode + MSP。
  • 首次启动：SVC 从任务栈恢复 PSP，然后返回 Thread/PSP。

权限边界

  • 非特权不能写 CONTROL、NVIC、SCB 等系统寄存器。
  • 非特权可以执行 SVC，主动请求内核服务。
  • MPU 可以把任务栈/外设划成非特权不可写。
先想一想

Handler Mode 下把 CONTROL.SPSEL 置 1，Thread 返回时会用哪条栈？

提示

SPSEL 只影响 Thread Mode；Handler Mode 仍用 MSP。异常返回时，EXC_RETURN 的 bit2 决定回 Thread 用 MSP 还是 PSP，和 Handler 期间 SPSEL 的值不是一回事。

04异常入口与硬件栈帧

异常入口是 M7 运行模型的核心：硬件自动把 8 个字压到当前栈上。点“触发异常”，一步一步看 SP 怎么下降、帧怎么长出来；再打开 FPU，看扩展帧和 lazy stacking。

SP = 0x20008000（异常前）
异常前：Thread Mode，PSP 指向任务栈顶。点“触发异常”开始压栈。
谁保存寄存器
硬件R0–R3、R12、LR、PC、xPSR
软件（PendSV）R4–R11；FPU 时另有 S16–S31
硬件（FPU 扩展帧）S0–S15、FPSCR、保留字

为什么是 8 个字？

AAPCS 把 R0–R3、R12 定为调用者保存；LR/PC/xPSR 是返回现场。R4–R11 是 callee-saved，留给软件保存。这样硬件帧最小，异常延迟低。

8 字节对齐

异常入口要求栈帧 8 字节对齐；如果 SP 不满足，硬件插入填充字，并在 xPSR bit9 标记。返回时按这个位恢复。

举一反三

FreeRTOS 的 pxPortInitialiseStack 构造的不是 8 字硬件帧，而是 17 字：8 字硬件帧 + 1 字 EXC_RETURN + 8 字 R4–R11。为什么多一个 EXC_RETURN？因为 PendSV 用 ldmia r0!, {r4-r11, r14} 把返回信息也放在任务栈上。第 8 节会逐行走。

先想一想

如果任务正在用 FPU，异常入口压的是 8 字还是 26 字？什么时候压 26 字？

提示

FPU 活跃时是 26 字（8 字基本帧 + 18 字扩展帧）。如果开了 lazy stacking，异常入口先只保留空间，等第一次 FPU 指令再写入 S0–S15/FPSCR；这就是第 5 节。

05FPU 扩展帧与 lazy stacking

M7 的 FPU 让异常帧从 8 字变成 26 字。lazy stacking 的目的不是“省寄存器”，而是“没用到 FPU 的任务不为它付栈空间和写入成本”。

FPU 未使用：异常帧 8 字（32 B），栈里没有 S0–S15/FPSCR。
场景帧大小
基本帧8 字 = 32 B
FPU 扩展帧26 字 = 104 B
扩展部分S0–S15 + FPSCR + 保留字 = 18 字

三个关键位

  • CONTROL.FPCA：任务是否使用过 FPU。
  • FPCCR.ASPEN：异常入口是否自动保留 FPU 空间。
  • FPCCR.LSPEN：是否启用 lazy stacking。

和 FreeRTOS 的关系

V10.5.1 的 pxPortInitialiseStack 不会预填 S16–S31；初始 EXC_RETURN=0xFFFFFFFD（无 FPU）。第一次 FPU 指令后，硬件才把 FPU 上下文纳入异常帧。任务栈预算要按 104 B 的扩展帧留余量。

写错会怎样

把任务栈按 32 B 帧估算，但任务实际用了 FPU：中断嵌套几层后栈溢出，表现可能是 HardFault、任务数据被踩、或“随机”复位。栈预算必须按最坏路径算。

先想一想

lazy stacking 开启后，异常入口还会写 S0–S15 吗？什么时候写？

提示

入口只保留空间，不立即写；第一次 FPU 指令触发写回。若任务一直不用 FPU，这部分空间就一直是保留状态。

06EXC_RETURN 与异常返回

异常返回不是普通 BX LR：LR 里装的是 EXC_RETURN，低 4 位告诉硬件“回哪个模式、用哪条栈、有没有 FPU 帧”。点不同值看解码。

先想一想

为什么 EXC_RETURN 的低 4 位不是普通地址的一部分？

提示

因为异常返回地址在栈帧的 PC 里；EXC_RETURN 是给硬件解码的控制字。低 4 位的组合表示模式/栈/FPU，不是跳转地址。

07NVIC、向量表、优先级、尾链

NVIC 决定“谁先跑、能不能打断、结束后要不要出栈再入栈”。M7 的优先级是数值越小越高；FreeRTOS 的临界区用 BASEPRI 只屏蔽一部分中断。

先想一想

为什么 FreeRTOS 的临界区用 BASEPRI，而不是 PRIMASK？

提示

PRIMASK 屏蔽所有可配置中断，会让高优先级中断也延迟；BASEPRI 只屏蔽“优先级数值 ≥ 阈值”的中断，保留高优先级（数值更小）中断的实时性。阈值就是 configMAX_SYSCALL_INTERRUPT_PRIORITY。

08SVC：启动第一个任务

FreeRTOS 不是“跳转”到第一个任务，而是用 SVC 触发异常，在 Handler 里把 PSP 指向任务栈，再用 EXC_RETURN=0xFFFFFFFD 返回 Thread/PSP。点“下一步”逐行走。

; prvPortStartFirstTask()
ldr r0, =0xE000ED08   ; VTOR
ldr r0, [r0]           ; 向量表基址
ldr r0, [r0]           ; 初始 MSP
msr msp, r0            ; 复位 MSP
mov r0, #0
msr control, r0        ; 清 FPCA，Thread 用 MSP
cpsie i / cpsie f      ; 开中断
svc 0                  ; 触发 SVCall
; vPortSVCHandler()
ldr r3, =pxCurrentTCB
ldr r1, [r3]
ldr r0, [r1]           ; 任务栈顶
ldmia r0!, {r4-r11, r14}
msr psp, r0
msr basepri, #0
bx r14                 ; EXC_RETURN=0xFFFFFFFD
初始：调度器即将启动第一个任务。点“下一步”。
栈指针内容说明
MSP0x2000A000SVC 硬件帧异常入口压在这里
PSP0x20008000任务初始帧17 字：8+1+8
任务初始帧：xPSR / PC / LR / R0 / EXC_RETURN / R4–R11。`ldmia r0!, {r4-r11, r14}` 弹 9 个字，PSP 指向剩下的 8 字硬件帧。
举一反三

为什么 SVC 的硬件帧在 MSP，而任务帧在 PSP？因为 svc 0 执行时还在 Thread/MSP；异常入口把 SVC 现场压到 MSP。Handler 里再把 PSP 指向任务栈，返回时 EXC_RETURN 指定 Thread/PSP，于是任务用自己的栈继续跑。

先想一想

ldmia r0!, {r4-r11, r14} 里的 r14 是什么？为什么不直接跳到任务函数？

提示

r14 是任务栈里的 EXC_RETURN（初始值 0xFFFFFFFD），不是普通返回地址。bx r14 让硬件执行异常返回流程：恢复 8 字硬件帧、切换 PSP、回到 Thread Mode。

09PendSV：真正的上下文切换

PendSV 是 FreeRTOS 的“切换开关”。异常入口已经把 R0–R3/R12/LR/PC/xPSR 压到任务栈；PendSV 只需要保存 R4–R11，再切换 PSP。点“下一步”看两个任务栈怎么交换。

; xPortPendSVHandler()
mrs r0, psp              ; 当前任务栈
ldr r3, =pxCurrentTCB
ldr r2, [r3]
tst r14, #0x10           ; FPU 上下文条件
vstmdbeq r0!, {s16-s31}
stmdb r0!, {r4-r11, r14} ; 软件保存
str r0, [r2]             ; 更新 TCB 栈顶
bl vTaskSwitchContext    ; 选下一个任务
ldr r1, [r3]
ldr r0, [r1]            ; 新任务栈顶
ldmia r0!, {r4-r11, r14}
msr psp, r0
bx r14                  ; EXC_RETURN
切换前：任务 A 正在运行，PendSV 已进入。硬件已把 A 的基本帧压到 A 的任务栈。

Task A

PSP_A

运行中 → 保存 R4–R11 → 栈顶写入 TCB_A。

Task B

PSP_B

就绪 → 从 TCB_B 取栈顶 → 恢复 R4–R11 → PSP_B。

PendSV 通常设为最低优先级，确保它不会打断高优先级中断；高优先级中断可以“迟到”并先执行。
举一反三

如果 PendSV 不是最低优先级，会发生什么？高优先级中断可能被切换流程延迟，实时性变差；更糟的是，PendSV 里调用 vTaskSwitchContext 时又被中断打断，栈/TCB 状态会变得难以推理。

先想一想

为什么 PendSV 保存 R4–R11，而不是 R0–R3？

提示

R0–R3、R12、LR、PC、xPSR 已在异常入口由硬件压栈；R4–R11 是 callee-saved，硬件不保存，必须由 PendSV 软件保存。两段合起来才是完整上下文。

10SysTick 与 tick

SysTick 只做两件事：把 tick 加一，判断要不要切换。它不直接做上下文切换，而是“挂起 PendSV”，让 PendSV 在合适的时候完成切换。

tick = 0 PendSV: 未挂起
T0SysTick 异常进入，Handler 使用 MSP
T1xPortSysTickHandler 调 xTaskIncrementTick
T2如果返回 pdTRUE，portYIELD_FROM_ISR 写 ICSR bit28
T3PendSV 挂起；SysTick 返回
T4PendSV 执行，完成上下文切换
tick=0：点“来一个 SysTick”。

关键寄存器/位

  • SysTick->CTRL/LOAD/VAL：tick 时基。
  • SCB->ICSR bit28：PendSV set。
  • portNVIC_PENDSVSET_BIT = 1 << 28。

为什么不直接在 SysTick 里切？

SysTick 可能和其他中断嵌套；把切换推迟到最低优先级的 PendSV，可以保证所有高优先级中断先处理完，切换时序更可控。

先想一想

如果 xTaskIncrementTick 返回 pdFALSE，还会进 PendSV 吗？

提示

不会主动挂起；只有需要切换时才写 ICSR bit28。但 PendSV 可能因为其他原因已经挂起，不能只看 SysTick。

为什么在 HardFault Handler 里读 CFSR 之前，要先确认 HFSR.FORCED？

提示

防跑偏三件事

1）不要把 x86 的调用栈直觉直接套到 M7：异常入口是硬件压栈，返回靠 EXC_RETURN。
2）不要混“硬件保存”和“软件保存”：R0–R3/R12/LR/PC/xPSR 是硬件；R4–R11 是 PendSV。
3）不要把 FreeRTOS 的 17 字初始帧当成 8 字硬件帧：多出来的是 EXC_RETURN + R4–R11。
