CPOL / CPH 如何改变首尾边沿语义

CPOL 决定 SCLK 空闲电平。CPH=0 适合从机在 CS 激活后已经提供首 bit 的情况，第一条边沿用于锁存；此时 SLSO 到首边沿的有效间隔是 T_LEAD + A×TQz。CPH=1 时第一条边沿先让从机 shift，下一条边沿再 sample；末边沿到 CS 释放的有效间隔是 T_TRAIL + (B+C)×TQz。注意两项量纲不同：LEAD/TRAIL 以 TPER 为基（×4^PRE），A/B/C 以 TQz 为基，相加前先各自换成 ns。

Slave mode 的行为固定为 CPOL=0、CPH=1，A/B/C 不用于移动从机采样点；从机在 SCLKI 下降沿采样。

示波器调试时应该按什么顺序调
  1. 先按从机手册确认 CPOL/CPH，避免把“边沿选错”误诊成“采样点太早”。
  2. 用 A 与 B+C 满足 tHIGH/tLOW，并补偿 pad/走线上升下降不对称。
  3. 固定 A、固定 B+C，再把 TQ 从 C 搬到 B，逐步后移 sample point。
  4. 在电压、温度、最长走线、最大负载和从机最大 tCO 下复测。

为什么同一个时钟在两章里叫 fQSPI 和 fPER

CCU 从全芯片视角把输出命名为 fQSPI；QSPI IP 章节从模块内部视角把进入状态机域的时钟称为 fPER。手册 §37.3.1 明确说明：CCU overview 中的 fQSPI，在本章作为 fPER 引用。二者不是两级额外分频。

建议的时钟初始化顺序
  1. 确保目标 QSPI 没有正在运行的 frame。
  2. 等待 CCUCON1.LCK=0，写 CLKSELQSPI=00B（停钟）。寄存器没有 UP 位：写操作本身会置起 LCK，改动被执行后硬件自动释放该位。
  3. 再写 CLKSELQSPI=目标源 + QSPIDIV；同样等 LCK 回到 0 再继续。
  4. 配置 GLOBALCON.TQ；再配置各 ECONz.Q/A/B/C。
  5. 用示波器确认 SCLK 频率、duty、CS lead/trail，而不是只相信寄存器计算。

不一定。若 QSPI 的独立 fQSPI 支路未变，fPER 与 SCLK 可保持不变；受影响的是总线侧 FIFO 服务能力。

跨时钟域缓冲：4×32 FIFO 与吞吐预算

Master 与 Slave 的 overflow / underflow 行为不同
  • 软件向满 TXFIFO 写：TX overflow，写入被忽略。
  • 软件读空 RXFIFO：RX underflow，并返回全 1。
  • 硬件向满 RXFIFO 写：RX overflow，本次写入被忽略。
  • Master 且 SRF=1：RXFIFO full 时协议可以暂停等待空间。
  • Slave 无法停止外部 SCLK，SRF 被忽略；TX underflow 时对外移出全 1。
跨域为什么会让某些状态看起来“慢半拍”

FIFO pointers、MC.CURRENT 与 phase/status 要从 fPER 域同步到 fSPB 域。同步链避免亚稳传播，却引入若干周期的可见延迟。手册对 MC.CURRENT 明确提示：更新会因异步 shift-engine domain 延迟若干周期。因此用这些状态做调试很合适，但不要假定它们与 pin edge 同周期更新。

DMA/中断阈值的工程设置
  1. 先算平均 entry rate：考虑 data packing、BACON entries、RX status injection。
  2. 测或估计最坏 DMA request-to-write/read latency，而不是平均 latency。
  3. TX 在 FIFO 仍有余量时提前请求；RX 在尚有足够 free space 时请求 drain。
  4. 错误 ISR 同时快照 ERRORFLAGS、FIFO levels、PHASE、DMA channel source/destination 与当前 BACON。

    LAST=0 之后发生了什么：TRAIL 是下限，WAIT/EXPECT 才是不定长的那段

    TRAIL vs WAIT
    DATA → TRAIL（定时长）→ WAIT / EXPECT（不定长）→ 下一个 block
    手册对 WAIT 的定义："The WAIT phase is simply a loop waiting for a write to the Tx FIFO, without predefined duration, and consequently without a defining bit field."（§37.3.2.1）
    情况block 之间的实际间隔说明
    下一个 entry 已经在 FIFO 里TRAILEXPECT 状态时长为 0，TRAIL 结束即开始下一块
    FIFO 暂时为空、稍后写入TRAIL + 等待时间等待时间取决于 CPU/DMA 何时写，无法由寄存器预设
    一直没有数据（Long / Continuous）不确定进入 EXPECT 并启超时计数（GLOBALCON.EXPECT，2⁶…2²¹ TPER）；超时后帧停住但 SLSO 不释放、置 ERRORFLAGS[7]、循环等软件介入
    一直没有数据（Short）Short 模式不经过 EXPECT，直接停在 WAIT 等写入
    超时计数从哪一刻开始（§37.3.2.6 原文）："after one FIFO entry has been shifted out and the module expects more bits to shift, according to the BACON.DL, a time-out counting starts." 锚点是当前 entry 全部移完、且还需继续移位那一刻——不是帧开始，也不是 TRAIL 结束。若那一刻下一个 entry 已在 FIFO 里，EXPECT 时长为 0，计数等于没启动。图 476 的状态序列是 Data → Trailing → Expect，TRAIL 这段固定延时照走。
    超时后的行为：帧停止但 SLSO 不撤；报 TO 中断并置 ERRORFLAGS[7]；状态机留在 EXPECT 里循环，原文 "generating an interrupt signal after each expect time interval"——即每个超时窗口再报一次，直到软件介入。
    超时值 GLOBALCON.EXPECT[13:10] 是指数编码：0H=2⁶ … FH=2²¹（单位 TQSPI，即 TPER），不是线性刻度。
    所以这句话要改成：TRAIL 是 block 间的最小间隔，不是实际间隔。用连续模式做流控时，真正的时序预算是"TRAIL + 供给延迟"，只算 TRAIL 会把最坏情况估短。
    另一个后果：EXPECT 超时后 SLSO 仍保持有效——外部从机看到的是"片选一直拉着、时钟停住"。如果从机有自己的超时保护，这段时间可能触发从机侧错误，需要在系统层面对齐。

    物理 FIFO 与逻辑 block

    PHYSICAL VS LOGICAL

    物理层：永远是 4×32-bit

    ENTRY 3 · 32 bit
    ENTRY 2 · 32 bit
    ENTRY 1 · 32 bit
    ENTRY 0 · 32 bit

    逻辑层：block 可以跨多个 entries

    d0 · 32b+d1 · 32b+rest=LONG D block
    例：10-byte Long block 需要 ceil(10/4)=3 个 DATA entries；最后一个 entry 只使用 2 bytes。

    Long 模式：一块跨多个 entry，SCLK 是否连续取决于供数

    D = ddddddb
    D = d d d d d b　（d = 满 32-bit entry，b = 末尾残余 entry）

    手册原文："One 'D' is made of a number of 32-bit TXFIFO entries 'd' and one rest at the end 'b'." DL 定义的是整块字节数，不是单个 entry 的长度；硬件按 DL 连续消耗多个 entry。

    DL = 5 字节（40 bit）

    需要 ceil(5/4) = 2 个 entry：entry0 = 4 字节（32 bit），entry1 = 1 字节（8 bit，只有低字节有效）。线上共 40 个 SCLK。

    DL = 32 字节（256 bit，上限）

    需要 8 个 entry，全部是满 32-bit。超过 32 字节就要转 XXL（DL=0 + XXLCON.XDL）。

    关键结论：entry 边界本身不插 gap。只要下一个 entry 在需要的那一刻已在 FIFO 里（EXPECT 时长 = 0），40 个 bit 就是连续发出的，SCLK 不停。bit 与 bit 之间没有分段，从机看到的就是一个 40 拍的连续帧。
    唯一的断点：供给不及时。若在 entry 边界处 FIFO 为空，硬件进入 EXPECT、SCLK 停住，等数据到了再继续（见第 05 章的 TRAIL/WAIT 说明）。这段停顿可能远长于一个 bit，部分从机会判为超时；因此 DMA 必须按 entry 速率提前供数，而不是等中断再补。
    残余 entry 与 MSB：一条容易被读反的手册要求
    BACON.MSB 的描述里写着："If the MSB option is set, and the data is a block longer than 32 bits, the block must be fed into the TXFIFO in reverse direction, from the end of the block until its beginning." 这句对应的是“每字内字节倒置”这个动作，具体见下面两种构造方式。
    拆开看：目标、直接写法、从字节数组构造
    目标只有一个——线上依次发出 01 02 03 04 05 06 07 08 09 0A（40 bit）。实现有两条路：

    方法 1 · 直接按字写入（推荐）：把要发的字直接写成 32-bit 常量。

    QSPI0->DATAENTRY[0].U = 0x01020304u;   /* 第 1~4 字节 */
QSPI0->DATAENTRY[0].U = 0x05060708u;   /* 第 5~8 字节 */
QSPI0->DATAENTRY[0].U = 0x0000090Au;   /* 残余字：有效字节在低位，高位补 0 */

    方法 2 · 从 uint8_t 数组构造：若数据本来就在字节数组里（如 DMA 源缓冲），必须让“按 32-bit 小端读出来的值”正好等于方法 1 的三个字。也就是每个字内部把字节倒着放：

    /* 每个 32-bit 字内部：低地址放低字节 */
uint8_t data[10] = { 0x04,0x03,0x02,0x01,   /* → 0x01020304 */
                     0x08,0x07,0x06,0x05,   /* → 0x05060708 */
                     0x0A,0x09 };           /* → 0x0000090A */

QSPI0->DATAENTRY[0].U = *(uint32_t *)&data[0];   /* 0x01020304 */
QSPI0->DATAENTRY[0].U = *(uint32_t *)&data[4];   /* 0x05060708 */
QSPI0->DATAENTRY[0].U = *(uint32_t *)&data[8];   /* 见下方注意 */
    方法 2 的两个前提：①data[] 必须 4 字节对齐（否则强制转换在 TriCore 上可能触发对齐 Trap）；②末尾只剩 2 字节，*(uint32_t*)&data[8] 会越界读 2 字节——应把数组补到 12 字节并置 0，或用 *(uint16_t*)&data[8] 读出后高位补 0。
    手册那句 "reverse direction, from the end of the block until its beginning" 对应的是方法 2 里的“每字内字节倒置”——把按发送顺序排的 01 02 … 0A 变成 04 03 02 01 …。它不是让你把残余字先写：三种方法下 entry 的写入顺序都是第 1、2、3 个字。
    如果不想手工倒字节：把源数组保持发送顺序，改用 ECON.BE 在数据通路上做字节置换——但 BE 的置换粒度是 16/32-bit 且作用于整个通道，要先确认它与你其余从机的字节序要求不冲突。

    Short 中“额外 DATA 自动复用配置”是什么意思

    当一个 short frame 完成后，如果 TXFIFO 还有 DATA entries，QSPI 可以使用上一份 configuration 自动开始新的 short frame。这不是说 FIFO 自动变成 16×8，也不是任意模式都复用；Long mode 完成声明的 block 后，额外数据不会被视为同一 block。

    Continuous mode 的本质是 CS 生命周期，不是新数据宽度

    Continuous 可以承载 short blocks，也可以承载 long blocks。LAST=0 时 SLSO 不释放，TRAIL 仍是每个 block 末尾的固定延时——它只决定 block 之间的**最小**间隔，不是实际间隔，SLSO 不释放；最终 LAST=1 时 TRAIL 才成为 frame 尾部并释放 SLSO。Long continuous 通常每个 block 仍需要 BACON，使用较大的 long block 可降低配置开销。

    ① 容量是被"32 bit"锁死的

    FIFO 物理宽度是 32 bit，出队时一次只能把一个字送进目标寄存器。于是"每帧都得改的东西"必须挤在同一个 32 bit 里。

    反证：如果 ECON 的 Q/A/B/C 也要跟着队列走，一帧就要两个 entry。对 16-bit 这种短帧，FIFO 开销直接翻倍、线端吞吐砍半；而 Q/A/B/C 在运行期几乎不变，为它付双倍代价没有任何收益。

    ② 判定准则只有一条：变化频率

    ③ 延时字段为什么是"3 bit 预分频 + 3 bit 计数"

    • 需求跨度有三个数量级：从机 tCSS 可能只有几十 ns（板级走线延迟量级），而某些器件的上电/转换/写周期要几十 µs；TPER 本身只有几 ns。
    • 只给计数字段不够：单靠计数要覆盖 2000× 约需 11 bit。
    • 硬件的解法：每个延时配一个 3 bit、每档 ×4 的预分频（40…47 = 1…16384），再乘 3 bit 计数的 1…8 → 单个延时覆盖 1…131072 TPER，约 217 的动态范围，只花了 6 bit。
    • 代价是分辨率变粗：n 越大步长越大。所以 LEAD、TRAIL、IDLE 各有独立预分频——LEAD 通常要细（几十 ns 量级），TRAIL 可能要很大（器件释放/写周期），互不将就。
    • 为什么是 ×4 而不是 ×2：同样 3 bit 预分频，×2 只能到 128，×4 能到 16384。用有限的位宽换更大的动态范围。

    ④ 为什么 CS 在最高位、LAST 在最低位

    • 硬件顺序：CS 是路由决策（选哪条 SLSO、哪份 ECON），必须最早解出；DL 紧随其后，因为移位计数器要按它装载。
    • LAST 只在帧尾看一次，放在最低位不占资源。
    • 工程副作用（不是设计目的，但很好用）：读十六进制时通道号一眼可见；b | 1 就是"结束这一帧"。

    ⑤ 为什么 16 个 CS 只配 8 份 ECON

    • 每份 ECON 背后是一整套通道时间量子分频器 + 相位时长控制。如果 16 个通道各配一套，硅面积与时钟树都按比例增加，而一个 ECU 很少需要 16 种不同的电气时序——所以按"够用的最小份数"给 8 份。
    • z & 7 是硬件里最便宜的映射：直接丢掉最高位。代价写进契约：CS2 与 CS10 必须共用同一 profile。
    • 所以 ECON 的分配单位是"从机类型"而不是"片脚"：同一颗 Flash 挂两个 CS 正好共享；两种不同器件恰好落到 z 与 z+8，就得改硬件连接或接受折中。

    ⑥ 为什么 ECON 必须驻留、不能帧中途改

    • ECON 改的是分频器和相位机本身。帧进行中改，会让同一位的前后半段用不同参数——位形状直接撕裂。
    • 所以它的生命周期是"板级配置期"，而 BACON 的生命周期是"一个 block"。把两者放在同一层，等于把"配置一次"和"每帧变化"混成一个生命周期。
    • 手册另有一条硬性提醒：3-wire 模式下 CPOL 或 CPH 改变时，必须先发一个 dummy frame，第一个真实帧之前引脚电平是未定义的。

    Chapter 08 · Slave select subsystem

    片选子系统：极性、使能、延时三组控制

    16 根 SLSO 只是起点。真正的问题有三个：从机要低有效还是高有效？16 根不够怎么办？某个从机要求片选比时钟晚一点又怎么办。QSPI 把这三件事都做成了寄存器——而且做成了与帧相位对齐的硬件行为，不是软件延时。

    SSOC · DEL0 · STROBE

    WHY

    片选必须与帧相位严格对齐；软件打拍子有抖动、占 CPU，而且一旦和 DMA 竞争就会错位。

    WHAT

    三件事可编程：每路的有效电平、每路的使能、以及 SLSO0 的延时选通（外部解复用用）。

    HOW

    SSOC.AOL/OEN 定电平与使能；GLOBALCON.DEL0 + STROBE 定 strobe；BACON.CS 的 4 bit 原样出脚做外部译码。

    三线模式：无片选时的帧边界

    3-WIRE
    好处：主机和从机各省一根引脚；单从机点对点时足够用。
    代价（手册自己的措辞）："less robust"——没有 SLS 就没有硬件帧边界，帧的起止只能靠数位数与 BACON.DL 对齐。

    三条连带后果：①配错 DL 时表现为整帧偏移而不是报错；②换 CPOL/CPH 时必须先发一个 dummy frame（手册明确）；③从机侧同理——有的流式器件只给时钟不给片选，此时靠"SCLKI 周期 > 2 个位时间"判定帧尾。

    推论：帧边界只有三个来源——片选线、位数、超时。选型时先问"这条链路有几个来源可用"，再决定 DL 与超时怎么配。

    流控：SRF 背压与三种 FIFO 中断模式

    §37.3.6 · GLOBALCON1

    WHY

    固定水线两难：中断太勤 CPU 扛不住，太懒 FIFO 见底。而纯边沿触发在"已空/已满"的静止态没有事件可发，DMA 链会停摆。

    WHAT

    ①SRF 背压：RXFIFO 满就停发时钟；②TXFM/RXFM 三种中断模式：Single / Batch / Combined。

    HOW

    GLOBALCON.SRF（仅主机）、GLOBALCON1.TXFM/RXFM + TXFIFOINT/RXFIFOINT 阈值。

    三种 FIFO 中断模式的触发条件

    TXFM / RXFM
    模式TXFM 编码中断何时触发一次搬几个失效模式（手册明写）
    Single Move01B每次写入后仍有空格就再请求；写满则不请求（防溢出），等移位读走一格再请求1用块 DMA 或多次写 → 多次中断 + 虚假的 transaction lost
    Batch Move10B水位跌破阈值那一刻（TX）；RX 是超过阈值那一刻N，且必须补回阈值以上补数太晚 → 追不回阈值 → 中断再也不来
    Combined00B水位 ≤ 阈值期间，每被取走一格就触发（RX 相反：≥ 阈值每写入一格）2（BACON + DATA1 成对）只搬 1 个 → BACON 那次中断被 DATA1 覆盖丢失
    先分清"模式"这个词：本表的 Single/Batch/Combined 是 FIFO 取数模式（TXFM/RXFM），与第 05 章的 Short/Long/Continuous 等数据模式完全无关——那套讲的是帧的边界，这里讲的是"什么时候叫人来搬"。
    下表两列以 TX 视角写；RX 侧方向相反：Batch 是水位超过阈值时触发、要搬到阈值以下；Combined 的 RX 每次写入触发、按需搬 1 格即可，不需要成对。
    阈值编码不一样，别照抄：TXFIFOINT 是 raw+1（00B=1 … 11B=4），RXFIFOINT 是 raw（00B=0 … 11B=3）。Single 模式下两个阈值都是 don't care——调它没用。

    阈值饥饿：中断不再产生的条件

    THRESHOLD STARVATION

    设 TXFIFOINT=10B（阈值 3），FIFO 深度 4。为看清推演，下面按"每个短帧只消耗 1 个 DATA 格"算（BACON 已预装、不计；若按 C+D 两格/帧，帧数减半，结论不变）：

    水位 4满
    取走 2 格
    水位 2 < 3触发中断
    本该补到 4
    DMA 迟到又发了两帧 → 水位 0
    一次补 2 格
    只到 2仍 < 阈值 3 → 无中断
    手册原话："the next interrupt would never come unless the filling level is being polled and the CPU keeps refilling in a loop until the threshold has been passed"。
    工程含义：Batch 模式下不能只补固定格数——必须查水位、补到阈值以上（理想是每次补满）。这也是现场"跑一会儿就停"的典型根因。

    Combined 模式：双中断与每次搬 2 个

    TWO CLOSE INTERRUPTS

    Combined 模式下，FIFO 每被取走一格就触发一次。而 BACON 和紧随其后的 DATA1 是连着被取走的，于是产生两个挨得极近的中断。BACON 那个几乎必然在 DATA1 到来之前没被服务 → 被覆盖丢失。

    正确：DMA 每次触发搬 2 个 move（transfer size = 2）。这样两个中断合成一次搬运，水位稳定。
    错误：一次只搬 1 个 → TXFIFO 平均水位一路下滑，最后在 0 和 1 之间振荡（连续模式除外）。DMA 报出的 transaction loss 应当忽略。

    背压：SRF 停止 SCLK

    SRF
    RXFIFO / 移位寄存器满软件来不及搬
    →
    SRF=1暂停 SCLK
    →
    从机被"挂住"不丢数据
    →
    软件腾出空间恢复
    为什么从机没有这个选项：从机不掌握时钟，SRF 在从机模式被忽略——它只能靠"及时清 RXFIFO"这一条软件策略。这是同一条物理事实的两面（见从机章）。
    代价：停时钟期间总线上没有任何进展。所以外部看门狗、从机的超时保护、以及你自己的时序预算，都要按最坏暂停时间算，不能按理想速率算。

    FIFO 未满时的溢出

    FALSE OVERFLOW
    手册明写：若 FPI 总线很慢而波特率很高，数据会在移位寄存器 → 未满的 RXFIFO 之间丢失，此时同样报溢出中断——尽管 FIFO 并没有满。

    诊断第一问就该是：我看到的是 FIFO level 还是 ERRORFLAGS？两者不矛盾——接收通路的"深度"不止 4 格，还包括移位寄存器到 FIFO 之间那一段没有名字的缓冲。

    对策：降低 fSCLK、提高 fSPB、或缩短"移位寄存器→FIFO"这一段的服务间隔。SRF 在这里帮不上忙——它没有阈值，只在 RXFIFO（或移位寄存器）已满时才停时钟；而假溢出恰恰发生在 FIFO 未满的时候。

    配置代码：两种典型组合

    SOFTWARE
    /* 场景 A：DMA 单搬 + 高波特率短帧 —— 保持 FIFO 尽量满 */
QSPI0->GLOBALCON1.B.TXFM     = 1;  /* 01B = Single Move         */
QSPI0->GLOBALCON1.B.RXFM     = 1;  /* 01B = Single Move         */
QSPI0->GLOBALCON1.B.TXFIFOINT= 2;  /* ★ Single 下 don't care    */
QSPI0->GLOBALCON.B.SRF       = 1;  /* 仅主机有效                */

/* 场景 B：块 DMA，一次 2 move —— Combined 是唯一正确选择 */
QSPI0->GLOBALCON1.B.TXFM     = 0;  /* 00B = Combined            */
QSPI0->GLOBALCON1.B.TXFIFOINT= 2;  /* 阈值 = raw+1 = 3          */
QSPI0->GLOBALCON1.B.RXFM     = 0;  /* 00B = Combined            */
QSPI0->GLOBALCON1.B.RXFIFOINT= 1;  /* 阈值 = raw  = 1           */

/* 场景 C：高波特率 + 短帧，想少进中断 —— Batch，但必须查水位补满 */
QSPI0->GLOBALCON1.B.TXFM     = 2;  /* 10B = Batch Move          */
/* 中断里：while (水位 <= 阈值) 继续补 —— 不能只补固定格数 */
    三个别踩的坑：①Single 模式下用块 DMA → 虚假 transaction lost；②Combined 下只搬 1 个 → BACON 中断丢失、水位缓慢下滑；③Batch 下只补固定格数 → 阈值饥饿，中断永久消失。

    自测与依据

    CHECK
    自测 1：把 RXFIFOINT 从 10B 改成 11B，接收中断会更频繁还是更少？
    更少。RXFIFOINT 是 raw 值，10B=2、11B=3；Combined 模式下要水位 ≥ 阈值才逐格触发，阈值抬高 → 触发点后移 → 中断更少。
    自测 2：Batch 模式下把阈值从 3 降到 2，能解决"跑一会儿就停"吗？
    能缓解但不能根治。阈值低意味着更早触发、更容易补回；但只要"补数间隔 > 阈值个帧的时间"，仍然会跌破。根治办法是中断里查水位、补到阈值以上（或补满）。
    自测 3：SRF=1 时，从机侧会看到什么？
    从机什么也看不到——SRF 在从机模式被忽略，主机也不会因为 SRF 而改变 SLSO。从机只会感觉"时钟怎么突然停了"。

    Chapter 10 · Phase events & error model

    相位事件 PT1/PT2 与九类错误标志

    普通 SPI 只在"传完一帧"给你一个中断，故障只有一个 overrun 位。队列化之后这两件事都不够用：软件要的动作发生在帧中间，而一次偶发错误无法定位就没有诊断价值。

    PT1 / PT2 / ERRORFLAGS

    WHY

    TBE 时补队列、RBF 时搬数、EOF 时放片选、进 EXPECT 时计超时——这些时刻都在帧中间。而错误若不能分类，ISR 只能"有错就整模块复位"。

    WHAT

    PT1/PT2 是事件多路选择器（8 选 1）；错误侧是 9 个粘滞位，各自可单独使能、单独清除。

    HOW

    GLOBALCON1.PT1/PT2 选事件，BACON.UINT 逐帧门控；错误侧 ERRORENS / ERRORFLAGS / ERRORCLEARS 三者同布局。

    PT1/PT2 事件编码（主机/从机）

    PT1 / PT2 编码
    编码事件主机侧含义从机侧含义
    000BBUSYWAIT 相位结束有发送数据在等时钟
    001BSCLKPCSCLK 极性切换（IDLEA/IDLEB 交界）—
    010BSOF帧开始收到第一个数据位（不是片选边沿）
    011BTBE发送缓冲被取空数据被移位引擎取走
    100BRBF接收缓冲被填满接收数据写入 RXFIFO
    101BEOF帧结束最后一位已收到；PT2 下固定表示 SLSI 撤销
    110BDNA数据未就绪 = 进入 EXPECT—
    111BCONTEXPECT 结束—
    为什么是"多路选择器"而不是"多根中断线"：不同驱动关心的时刻完全不同——有的要在 SOF 打时间戳，有的要在 TBE 触发 DMA，有的要在 DNA/CONT 上量 EXPECT 时长。硬件不可能为每种需求都做一根线，于是让软件从一张事件表里挑两个（PT1 一个、PT2 一个）。
    从机的特例：PT2 在从机模式下只有 SLSI 上升沿能触发，且必须写 101（EOF）这个编码——这是硬件约定，不是笔误。PT1 的 SOF 在从机侧也换了定义：绑"收到的第一个时钟脉冲"，因为从机自己没有"开始发送"这个动作。

    BACON.UINT 与 User Interrupt

    PER-FRAME GATING

    全局中断使能有个副作用：每一帧都会来。可有些测量只关心特定一帧——比如只在某条命令帧上量从机响应时间。手册的做法是把使能位放进 BACON：

    BACON.UINT = 1 → PT1 事件路由到 User Interrupt；它不是只对这一帧有效：从这一帧起、在后续帧中持续产生，直到下一个 BACON 把 UINT 写成 0
    注意它和 MC 的 IBL/IAL 不是一回事：Move Counter 的两个中断复用 U 线但不受 UINT/USREN 控制。所以进 MC 的中断服务程序时，必须自己查 MCCON.IBLF/IALF 才能分清是谁触发的。

    九类错误标志及其归属

    ERRORFLAGS[8:0]
    位值错误谁的责任典型触发场景
    0001HParity Error链路 / 对端PAREN=1 时收到的校验位不符
    1002HUnexpected Configuration软件该发 D 的时头发了 C —— 通常是 DMA 源指针错位
    2004HBaud Rate Error主机 / 链路从机看到 SCLK 频率超出合法带或毛刺
    3008HTXFIFO overflow软件往满 TXFIFO 里继续写（本帧写入被忽略）
    4010HTXFIFO underflow主机（从机视角）从机首边沿到达时 FIFO 为空 → 移出全 1
    5020HRXFIFO overflow软件 / 带宽RXFIFO 满时硬件仍要写（含"没满也可能溢出"的假溢出）
    6040HRXFIFO underflow软件读空 FIFO（返回全 1）
    7080HEXPECT time out主机 / 队列供给多 entry 帧中途断供，超时窗口用尽
    8100HSLSI misplaced inactivation主机（从机视角）从机帧中途片选被撤销
    "谁的错"这一列才是诊断价值所在：看到 008H（TX overflow）就该去查写侧的节流，而不是查从机；看到 010H 则相反——那是主机没喂数。同一个"FIFO 出错"的笼统说法，在这一列里被拆成了完全不同的排查方向。

    ERRORENS / ERRORFLAGS / ERRORCLEARS

    ENS · FLAGS · CLEARS

    ERRORENS

    9 位，逐类使能中断。分级响应的基础：安全相关错误单独送一路、可恢复错误走另一路。

    ERRORFLAGS

    9 位粘滞标志。写 1 置位并触发中断，写 0 无效——正是"软注入自检"的入口。

    FLAGSCLEAR.ERRORCLEARS

    9 位，只写，读回 0。写 1 清除对应标志。不能读-改-写，因为标志会被硬件异步置位。

    为什么必须是"写 1 清除"：如果允许读-改-写，那么在读与写之间新到的错误会被这次写覆盖掉——一次偶发故障就此消失。写 1 清除让"清谁"与"当前有哪些"解耦。
    软注入的用途：不接外部从机、不产生真实线端事件，也能验证"标志置位 → 中断路由 → ISR → 安全反应"整条链是否完好——这是功能安全自检里最便宜的一环。配合 GLOBALCON.LB（内部回环）可以再验一层数据通路。

    代码与自测

    SOFTWARE / CHECK
    /* 关心"帧结束"和"进入 EXPECT"两个时刻 */
QSPI0->GLOBALCON1.B.PT1 = 5;      /* 101B = EOF  */
QSPI0->GLOBALCON1.B.PT2 = 6;      /* 110B = DNA（进 EXPECT）*/
QSPI0->GLOBALCON1.B.PT1EN = 1;
QSPI0->GLOBALCON1.B.PT2EN = 1;

/* 只对这一帧武装用户中断 */

QSPI0->BACONENTRY.U = b;

/* 错误侧：只放行"软件自己造成的"和"链路层"的 */
QSPI0->GLOBALCON1.B.ERRORENS = 0x1E6;  /* bit1,2,5,6,7,8 */

    自测 1：为什么 PT2 在从机模式必须写 101？
    因为从机侧 PT2 只有 SLSI 上升沿一个事件源，而 101（EOF）在从机语义下正好被重定义为"SLSI 撤销"。手册明确要求"always use the setting 101"。
    自测 2：看到 010H（TXFIFO underflow），该查哪一侧？
    查主机——这是从机视角的错误：从机首边沿到达时 TXFIFO 是空的。说明主机（或驱动它的 DMA）没在帧开始前预装数据，不是从机的问题。
    自测 3：用 read-modify-write 清错误标志，会有什么后果？
    可能丢新错误：读与写之间硬件又置起了新的错误位，而写回的是旧值。必须用 FLAGSCLEAR 的写 1 清除。

    Chapter 11 · Observability

    非侵入观测：RX_EXITD 与状态注入

    读 RXFIFO 会推进读指针，调试读取将改变被测状态。部分状态字段跨时钟域同步，读数存在固定延迟。本章给出各观测量的精度边界。

    RXEXITD · PHASE · BITCOUNT

    WHY

    在线调试时，读一次 FIFO 就等于替软件消费了一个数据；诊断超时时，看"传了多少字节"往往答不到点子上。

    WHAT

    两条读路径（破坏性 / 只读镜像）、三组进度量（PHASE / BITCOUNT / MC.CURRENT）、一个注入机制（SI）。

    HOW

    RX_EXIT vs RX_EXITD；Cerberus 按总线 master tag 识别"旁观者"；GLOBALCON.SI 把状态写进 RXFIFO。

    RX_EXIT 与 RX_EXITD

    090H vs 094H
    RX_EXIT（090H）RX_EXITD（094H）
    语义正常出队调试/镜像读
    读指针推进——读一次就消费一个 entry不推进
    谁该用驱动 / DMA调试器、Trace、安全监控任务
    用错的后果—用 RX_EXIT 看一眼 → 软件少收一个数据，且毫无报错
    还有一层身份识别：手册明确，通过 Cerberus（由 FPI master tag 识别）读取 FIFO 条目不会修改 FIFO 内容，也不会动读写指针。也就是说，"谁在读"这件事本身参与了语义——同一个地址，调试主机读和 CPU 读，结果不同。

    PHASE / BITCOUNT / MC.CURRENT 的精度

    PHASE / BITCOUNT / MC.CURRENT
    量告诉你什么不可信的地方（手册原话）
    STATUS.PHASE当前/上一个帧相位读到的往往是上一个相位——高速时等你读到，相位已经走过去了
    STATUS.BITCOUNT已移出的位数，支持到 256"The value is not accurate; it may be lower than the number of bits shifted"。>0 只表示"正在传"
    MC.CURRENTMove Counter 还剩几块从移位引擎的异步时钟域同步回来，读数有几拍延迟
    使用原则：这三个量适合回答"卡在哪个阶段""还在动吗"，不适合做精确时序测量或位计数。要精确结果，用线端波形或计数器外设，不要用这些状态位。
    诊断第一问该换：不是"传了多少字节"，而是"现在停在哪个相位"。PHASE 停在 EXPECT 说明在等数据；PAUSE 没有独立的 PHASE 编码——它的判据是 EN=0 且 PHASE=0（Wait），且 PHASE 只在主机模式有效、从机恒为 0（PAUSE 的完整语义见第 12 章）。这一问能把"卡住"拆成几种完全不同的原因。

    状态注入（GLOBALCON.SI）

    GLOBALCON.SI

    GLOBALCON.SI=1 后，每个数据块之后（取决于 BACON.DL/BYTE）硬件会把 STATUS 的内容作为一个条目写进 RXFIFO。于是"数据"和"该数据的元信息"排在同一条队列里，DMA 一次搬走，不需要额外一次中断去读寄存器。

    一条必须知道的限制：注入条目里只有 bit 22…31 反映注入那一刻的状态（即最新帧）；其余位受流水线影响，装的是非最新信息。所以注入状态值钱的是高 10 位，别拿低位做逐帧判断。

    为什么需要它：ERRORFLAGS 是粘滞的，它回答"出过错"，回答不了"哪一帧出错"。多帧排队之后，状态寄存器早被下一帧覆盖了——只有随数据流一起走的标签才能定位到帧。

    自测与依据

    CHECK
    自测 1：调试时想确认 RXFIFO 里下一个值对不对，该读哪个地址？
    RX_EXITD（094H）。读 RX_EXIT 会把数据消费掉，软件那边就少了一个——而且不会有任何错误提示。
    自测 2：BITCOUNT 显示 128，能断定已经移出 128 位吗？
    不能。手册明说它不精确，可能低于实际位数；它只保证">0 表示正在传输、末位之后归零"。
    自测 3：要逐帧判断"这一帧是不是 parity 错"，读 ERRORFLAGS 够吗？
    不够。ERRORFLAGS 是粘滞的、全局的，多帧之后无法归因。应打开 GLOBALCON.SI，让状态随数据进 RXFIFO，并按 bit 22…31 判断。

    依据：TC3xx UM Part 2 V2.0.0 §37.3.4.1（OCDS Suspend 内的 Cerberus 读取说明：不修改 FIFO 内容与读写指针）、STATUS.PHASE 说明（"shows a previous phase"）、STATUS.BITCOUNT（"not accurate"、256、末位归零）、MC.CURRENT（异步时钟域延迟）、GLOBALCON.SI（每数据块后注入、仅 bit 22…31 反映最新帧）、RX_EXIT(090H)/RX_EXITD(094H) 寄存器表。

    Chapter 12 · Lifecycle

    暂停、睡眠与复位的粒度

    队列外设没有天然静止点——软件要改配置时，无法预测"现在改会不会踩到正在发的帧"。硬件给的答案是几种粒度不同的停下来：有的等帧尾，有的立刻冻结，有的顺手把配置也清了。

    EN · RESETS · OCDS

    WHY

    在半个 bit 上停止，外部从机会把半帧当成完整帧；而全模块复位又会把辛苦排好的队列和 ECON 一起清掉。

    WHAT

    PAUSE（等 TRAIL）／sleep（关双时钟）／OCDS 软挂起／硬挂起／两级软件复位／AREN 自动刹车。

    HOW

    GLOBALCON.EN 请求、STATUS.PHASE=0 确认、RESETS[31:30] 两位编码、OCS.SUS、KRST0/1。

    PAUSE：请求与完成的判定

    EN / PHASE
    写 EN=0只是请求
    →
    硬件等等到最后一个 TRAIL 结束
    →
    进入 PAUSEEN=0 且 PHASE=0
    为什么必须等 TRAIL：在帧中间停，从机会看到"时钟停了但片选还拉着"或"半帧"——某些器件会把半帧当成完整帧处理，数据就错位了。PAUSE 的判据是 EN=0 且 STATUS.PHASE=0（仅主机），不能只写 EN 就认为停了。
    软挂起走同一条路：OCDS soft suspend 请求后，硬件也是在 TRAIL 结束时进 PAUSE，然后给出 acknowledge。而 hard suspend 立即冻结一切——包括服务请求线，现场保住了，但总线处于非法中途状态。

    sleep 与 PAUSE 的时钟差别

    SLEEP
    PAUSE：状态机停，时钟还在。寄存器可读写，可随时恢复。
    sleep：fSPB 与 fPER 都被关掉。寄存器访问与状态机一起停摆。

    什么时候可以进 sleep（从机侧）：无待发队列、无进行中传输、TXFIFO 为空——三条同时满足。为什么：sleep 是系统级广播，模块只能选"什么时候可以接受"；如果正在 long/continuous 等数据时被关时钟，"等数据"就变成了永久等待。不想被 sleep 打断时，可以用 CLC.EDIS 关掉该模块的 sleep 使能——这是"拒绝"，不是"延后"。

    从机唤醒路径：sleep 期间 QSPI 自己不可能检测边沿（时钟都关了），必须靠 SCU.ERU 在 SLSI 引脚边沿触发把系统叫醒，唤醒后模块落回 PAUSE，再由软件恢复。

    复位的三种粒度（RESETS）

    RESETS[31:30]
    编码复位什么配置还留着吗什么时候用
    00B不复位——
    01B状态机 + TXFIFO + RXFIFO留着（寄存器不动）协议失步、从机重启后快速恢复通信——"避免重新配置整个 IP"
    10B寄存器全清要换一套完全不同的配置
    11B状态机 + FIFO + 寄存器全清彻底重来
    KRST0/1整个模块内核全清需要连内核逻辑一起复位时，用这套独立机制
    两条容易踩的：①RESETS 要求时钟使能才能用（CLKSEL），且复位时长约等于SPB 与内核两者中较慢时钟的 10 倍——写完就立刻读状态是不可靠的；②用 10/11 复位后 CLKSEL 也会被清掉。

    AREN：从机时钟错误时自动清 EN

    AUTO RESET ENABLE

    GLOBALCON.AREN=1 时，从机侧检测到时钟异常（尖峰 / 波特率偏差）后，硬件在置标志、发中断之后会自动清 GLOBALCON.EN，把模块踢回 PAUSE。

    适用范围别放大：AREN 只挂在从机的两类时钟监测（spike / baud rate）上，不是"任何错误都自动停机"。主机侧的错误（overflow / underflow / EXPECT timeout）不会触发它。
    为什么需要"自动"：从置标志到软件进 ISR 之间有一段真实延迟。这段时间里如果继续收，后续帧会被已经错位的状态机继续污染。让硬件自己停下，等于把"检测 → 上报 → 停摆"做成一条闭环，软件只负责善后。

    自测与依据

    CHECK
    自测 1：写完 EN=0 后立刻去改 ECON，安全吗？
    不安全。EN=0 只是请求，硬件要等最后一个 TRAIL 结束才真正进 PAUSE。必须轮询到 EN=0 且 PHASE=0（仅主机）再改。
    自测 2：从机被主机重启、协议失步，用哪种复位最快恢复？
    RESETS=01B：只复位状态机与两个 FIFO，ECON/BACON 配置全部保留，复位完就能重新通信。用 10/11 会把配置清掉，得重排整条队列。
    自测 3：调试器设断点后，用哪种挂起才能保住时序现场？
    hard suspend——立即冻结一切（含服务请求线），现场最完整，但外部从机看到的是"半帧"。若要对外部从机友好，用 soft suspend，它会等 TRAIL 结束再停。

    依据：TC3xx UM Part 2 V2.0.0 §37.3.4（PAUSE 等 TRAIL、sleep 关 fSPB+fPER、OCDS 软/硬挂起）、GLOBALCON.EN/AREN 描述、GLOBALCON.RESETS 四位说明（01/10/11 语义、CLKSEL 依赖、10×慢时钟时长）、KRST0/KRST1、OCS.SUS/SUSSTA、§37.3.8.2（ERU 唤醒）。

    Closing · Design philosophy

    设计原则与选型表

    前十二章的机制可归为四条原则：量化时间、外化状态、守卫边界、非侵入观测与恢复。

    SYNTHESIS

    四条设计原则

    FOUR PRINCIPLES

    ① 时间必须被量化，硬件才可能替软件守时

    TPER → 模块 TQ → 通道 TQz → A/B/C，全是一个 TQ 的整数倍；五相语法、4PRE 预分频也是同一思路。量化到什么程度？量化到"一条寄存器写就能表达一个时间"。

    ② 状态必须被外化，软件才能用一条 32-bit 写表达意图

    FIFO 队列、BACON/ECON 两层、按地址路由的 entry 类型、Move Counter 计数器——都是把"我现在想干什么"变成"往哪个地址写哪个值"。

    ③ 边界必须被守卫，系统才敢把安全功能挂上去

    EXPECT 超时、从机时钟监控、九类错误、AREN 自动停机。守卫的含义是：出错即置标志、可分级、可停摆，而不是"希望软件及时发现"。

    ④ 观察与恢复不能破坏现场

    RXEXITD、Cerberus 读取、PAUSE、分级复位、软挂起。恢复粒度细到"只重启通信、不重配"，在线调试才有意义。

    Appendix · HSIC

    HSIC：QSPI IP 内的输入捕获子模块

    HSIC 是与 SPI 无关的输入捕获子模块，与通信引擎共享同一 IP。手册给出的用途是：为 ADAS 应用测量相对低速的输入信号。

    §37.4 · CAPCON

    WHY

    ADAS 要测转速、占空比、PWM 反馈这类低速信号。用 CPU 打时间戳太贵，占一个 GPT/CCU 通道又浪费——同一个 IP 里塞一个捕获定时器最省。

    WHAT

    15-bit 计数器（分辨率 fPER）+ 四种测量模式（R→R / R→F / F→R / F→F）+ 一个 CAPCON 寄存器。

    HOW

    CAPCON.EDGECON 选模式、INS 选输入、EN 使能；捕获值进 CAP，中断走 HC 线。

    四种捕获模式

    MEASUREMENT
    模式测的是什么典型用途
    R→R（rising to rising）整个周期转速、脉冲频率
    R→F（rising to falling）高电平时间PWM 高相宽度
    F→R（falling to rising）低电平时间PWM 低相宽度
    F→F（falling to falling）整个周期（从下降沿起算）与 R→R 互补，用于极性不确定的信号
    分辨率是 fPER，量程要自己算：15-bit 计数器的最大计时 = 215 × TPER。fPER=100 MHz 时 ≈ 32768×10 ns = 328 µs（对应 ≈3.05 kHz）；fPER=200 MHz 时只有 164 µs（≈6.1 kHz）。对照手册给的验证范围 3 kHz…30 kHz：100 MHz 下满量程 ≈3.05 kHz，3 kHz 已略超出量程；200 MHz 下 ≈6.1 kHz，3 kHz 根本测不到。换更快的 fPER，可测下限会同比例抬高——这一点常被忽略。

    CAPCON 寄存器

    0A0H
    字段位作用
    CAP[14:0]14:0捕获到的计数值（只读）
    OVF[15]15溢出：信号周期长到计数器绕回，说明超出量程
    EDGECON[17:16]17:16边沿配置——决定上面四种模式里的哪一种
    INS[19:18]19:18输入源选择
    EN[20]20使能 HSIC
    CAPC / CAPS28 / 29标志清除 / 置位（写 1 生效）

    CAPSEL31中断选择（决定是否走 HC 中断线）
    一个必须处理的初始化陷阱：手册明确——使能（CAPCON.EN=1）之后第一次捕获可能是随机值，取决于使能瞬间输入信号的电平。软件必须丢弃第一次捕获结果，否则会读到一个看起来完全合理的错误值。

    与 QSPI 的关系：共享 IP 与生命周期

    COEXISTENCE

    共享什么

    同一块 IP 的寄存器空间与 fPER 时钟基准；捕获中断走 HC 中断线，与 QSPI 的 TX/RX/ERR/PT/U 分开。

    不共享什么

    数据通路完全独立：HSIC 不碰 FIFO、不碰移位引擎、不受 BACON/ECON 影响。但它随 QSPI 内核一起休眠/挂起——这条耦合在系统集成时必须知道。

    选型含义：HSIC 是"定时器资源复用"的一条捷径——不必为一路转速信号占用一个 GPT/CCU 通道。代价是：分到 HSIC 的那个 QSPI 实例通常就不再用于通信，而且不是所有派生型号都带这个子模块，移植前要按具体型号核对。

    自测与依据

    CHECK
    自测 1：量一个 200 Hz 的轮速信号，HSIC 合适吗？
    不合适：200 Hz 的周期 5 ms，比手册下限 3 kHz（周期 333 µs）还慢约 15 倍，而 15-bit 计数器在 fPER=100 MHz 时最大也只有 328 µs，必然溢出（OVF 置位）。量更慢的信号要换定时器，或在外部先分频。
    自测 2：使能 HSIC 后第一次读到的 CAP 值能用吗？
    不能。手册明确第一次捕获可能是随机值，必须丢弃。正确做法是使能后先等一次捕获并丢弃，再从第二次开始使用。

    依据：TC3xx UM Part 2 V2.0.0 §37.4 Functional Description HSIC（四种测量模式 RR/RF/FR/FF、15-bit 计数器、分辨率 fPER、HC 中断、首次捕获随机值须丢弃、验证频率 3 kHz…30 kHz）、CAPCON 寄存器描述（0A0H，CAP[14:0]/OVF/EDGECON/INS/EN/CAPC/CAPS/CAPF/CAPSEL）、Feature List "High Speed Input Capture (HSIC)"。

    Chapter 09 · Slave mode

    从机模式：固定时序与重定义的帧边界

    前八章为主机视角。从机不掌握 SCLK 与 SLSI，帧边界、时序参数与超时判据因此另行定义；BACON/DATA 队列接口保持不变。

    PASSIVE CONTRACT · §37.3.3

    WHY · 为什么车规要做从机

    域控、SBC、安全芯片常把 MCU 当外设来读。主控随时可能开始或停止时钟，MCU 既不能拉低 SCLK 也不能插等待，只能"立即响应"。

    WHAT · 被动语义

    CPOL/CPH 固定 0/1、A/B/C 与所有延时失效、SLSI 定帧、DL 限 2…32 bit、SRF 被忽略、波特率字段改当看门狗。

    HOW · 入口

    GLOBALCON.MS=1x；PISEL 选输入引脚与电平；SLSI 撤销即复位移位状态机；PT2 绑 SLSI 上升沿（事件编码表见第 10 章）。

    主从资源归属对照

    WHO OWNS WHAT

    SCLK产生接收，只做采样从机没有任何"插等待"的能力
    片选驱动 SLSO[15:0]接收 SLSI（固定低有效）极性不可配，接反了整帧都不来
    帧边界BACON.LAST 决定SLSI 撤销，或位数从机的"帧"是外部事件，不是配置

    A/B/C 延时与采样点有效全部失效采样固定在 SCLKI 下降沿

    首拍竞态：TXFIFO 必须在首边沿前就位

    FIRST-EDGE RACE
    手册原文的两种失效：①首边沿到达时 TXFIFO 为空 → 欠载，对外移出全 1，置 underflow 错误；②软件恰好在首边沿那一刻写入 → 仍然报欠载，而且"数据可能被破坏——首 bit 会是 1"。第二种最容易忽略：你以为写了，实际首 bit 已经错了。
    工程做法：从机侧不能"来一个边沿补一次数"。要么在帧开始前把 TXFIFO 灌满，要么用 PT1 的 BUSY/TBE 事件（事件表见第 10 章）在上一帧就提前准备下一帧——这也是为什么从机驱动通常把 TX 队列做成"预装 N 帧"而不是"按需喂"。

    从机波特率：时钟监测的参考值

    CLOCK MONITORING
    动机：从机拿不到时钟，也就无从判断"这个边沿该不该来"。手册原话：SCLK 上的窄毛刺（地弹、过冲振铃）会让从机多打一拍——多出来的这一位被塞进前端 RXFIFO，于是之后所有帧都永久移位。这是 SPI 从机最隐蔽的失效：数据看着像真的，只是从这一位开始全错位。

    单位先定义清楚：本节的"标称位时间" Tbit = (A+1+B+C) × TQz，TQz = TPER×(TQ+1)×(Q+1)，以本机 fPER 为基准。从机不知道主机的实际配置，只能拿自己 ECON 里那组参数作判据——这正是"同一组字段、两种语义"的由来。

      为什么从机要保留整套 BACON/DATA 队列

      手册明确："the slave mode supports the same user interface as the master mode. This means the BACON-Data sequences remain the same." 这是有意的设计：驱动栈只写一套描述逻辑，主从由 GLOBALCON.MS 切换。

      但代价是字段语义分裂——同一个 BACON.LAST，主机里决定"片选何时释放"，从机里几乎无事可做（帧边界由 SLSI 或位数决定）；同一个 ECON.Q/A/B/C，主机里造波形，从机里划合法带。读手册时必须按模式切换语义读同一张位域表，这是最容易踩的认知陷阱。

      为什么主从切换一定要模块复位

      主机模式下，状态机是"定时器驱动"：按 TQ 计时、按 A/B/C 输出边沿。从机模式下它是"事件驱动"：每个外部边沿触发一次动作。两者共用移位通路与计数器，但驱动源完全不同。

      直接改 MS 位，等于把正在计时的定时器突然改成计数器——残留的相位、未清的中断标志、已装了一半的移位寄存器都会带进新模式。手册因此要求：先回 wait、复位状态机、再进从机。

      从机怎么被"叫醒"：SLSI 边沿经 SCU.ERU

      休眠时 QSPI kernel 时钟已关，模块自己不可能检测边沿。唤醒必须走系统级路径：SCU.ERU 在 SLSI 引脚的可编程边沿上触发软件中断，把 MCU 叫醒，唤醒后模块落回 PAUSE 状态，再由软件恢复。

      设计含义：从机侧的低功耗不能只考虑 QSPI，必须同时配好 ERU 的边沿选择与唤醒源使能——这是"外设能力"和"系统能力"必须一起规划的例子。

      STIP：取消选择时 MRST 输出什么电平

      从机在被取消选中（SLSI 撤销）时，MRST 应该输出 0 还是 1？手册给了一位专门控制它：GLOBALCON.STIP。0 表示取消选择时 MRST=0，1 表示 MRST=1。

      这不是小事：主机侧可能用上拉/下拉判断从机是否在线，或者把 MRST 当"数据有效"看。默认电平选错，主机会读到伪数据。选型时按对端 EVAL 的期望配。

      自测：从机模式下把 ECON.A 从 3 改成 0，采样点会前移吗？
      不会。A/B/C 在从机模式不参与采样，手册明确"the settings for the leading, trailing, idle delays, and duty cycle and sampling point are irrelevant"，采样固定在 SCLKI 下降沿。改 A 只会影响波特率看门狗的分频基准。
